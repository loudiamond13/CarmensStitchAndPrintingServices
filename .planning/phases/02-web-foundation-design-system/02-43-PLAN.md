## Review Findings Being Closed (02-REVIEW-g199-42.md, owner ruling 2026-10-13, UAT 199 close-out)

**WR-01:** a press on the dark area that does not close the dialog (middle, right, a primary press followed by a scroll, a press on the backdrop's scrollbar) runs the browser's default focus change: `main` (tabIndex -1) gets focus, and the trap's `onFocusIn` calls `focusFirst()`, which focuses the header's Close button without `preventScroll`. The caret leaves the confirm field and a scrolled backdrop jumps back to the top. The E2E checks only looked at `toBeVisible()` and `toHaveValue()`, from an unscrolled backdrop, so they could not see it.

**WR-02:** plan 02-42 hid that focus scroll from the close rule by re-reading the press snapshot at every focus-in and once more in a 0 ms timer. That depends on WebKit's task order and accepts any real scroll inside the window.

**Owner decision (LOCKED for this plan):** one shared fix in `web/src/ui/overlays/useFocusTrap.ts`: focus that leaves an open overlay returns to the last focused element inside it (not the first tabbable), with `focus({ preventScroll: true })`, so the scrolled backdrop does not jump and the caret stays in the confirm field. That removes the cause WR-02's workaround hid, so the workaround goes. The review's suggested code is a starting point, not binding. Every overlay uses the trap: initial focus, Tab wrap, Esc, restore-on-close, the toast-layer exemption and the stacking via `isTop` stay as they are, and are regression-tested.

**Locked context:** D-42 ("Pressing the backdrop's scrollbar never closes the dialog, so typed confirm text is never lost"), D-08 (a look change stops for the owner), D-33 (utilities only, no inline style or style write, strict CSP), D-07 (SPEC-DEVIATION markers stay accurate).

## Design (Claude's discretion inside the owner's decision)

1. **Remember, seeded.** `activateTrap` keeps one local variable, `lastInside`, holding an `HTMLElement` or `SVGElement` inside `root`. It is seeded right after the initial focus is placed, from `document.activeElement` when the trap's root contains it. The review's sketch started it at `null`, and that would miss the main WR-01 case: the person types into the field the trap focused on open and never moves focus, so no focus-in is ever seen inside. Every focus-in whose target is inside `root` updates it, in every trap, top or not. A trap below the top one only records its own last element and never pulls focus.
2. **Return without scrolling, or fall back.** On a focus-in outside `root` (and outside the toast layer) while the trap is the top one: if `lastInside` is still connected and still inside `root`, call `lastInside.focus({ preventScroll: true })`. If focus did not land there (`document.activeElement !== lastInside`, for example the element became disabled or inert), or there is no usable `lastInside`, call the existing `focusFirst()`. That keeps the old behaviour, including its scroll-into-view, so focus never stays outside the dialog and the person can see where it went.
3. **Nothing else moves.** `focusFirst`, `onKeyDown` (Tab, Shift+Tab, toasts), the activation rules, the trigger restore and the cleanup's `below.focusFirst()` are unchanged. The new state lives in the plain `activateTrap` function, never in hook state, so the React Compiler output of `useFocusTrap` does not change.
4. **WR-02 cleanup.** With the trap no longer scrolling, Modal's focus re-read and its deferred timer have nothing left to hide. They are deleted, and the two unit tests that pinned them are inverted.

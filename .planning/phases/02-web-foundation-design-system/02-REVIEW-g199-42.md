# Phase 2: Code Review Report (gap G-2-199, plan 02-42, D-42)

**Reviewed:** 2026-10-13T20:56:08-05:00
**Depth:** standard
**Files Reviewed:** 11 (10 changed, plus `useFocusTrap.ts` for context)
**Status:** issues_found

## Summary

Plan 02-42 changes how the Modal scrim closes. It used to close on a mousedown. Now it closes on a primary-button click that follows a primary-button press on the scrim, off any classic scrollbar, with every scrim at the same scroll position at the press and at the click. Scrolls caused by moving focus are re-read at each `focusin` while a press is pending, and once more a task later. The plan also adds two Chromium Playwright projects with real scrollbars and moves the Delete Order helpers into a shared module.

I traced the core rule and found it correct:
- The overlay and region listeners both run for one mousedown. Each recomputes the same snapshot, because the check uses `event.target`, not `currentTarget`.
- The first `onClick` uses up the pending press, so the bubbled call does nothing.
- A press that starts inside the dialog clears the pending press, so text selected from the field out onto the backdrop never closes the dialog.
- The timer is cleared on cleanup and guarded by `pendingPress !== null`, so it cannot leak or act after unmount.
- Esc, `loading`, the nested-overlay Esc rule (UI-WR-01) and the focus-trap stack are unchanged.
- Closing on click also removes the old click-through, where a mousedown close let the mouseup and click land on the page under the scrim.
- Port 5199 and `reuseExistingServer: false` are unchanged. The two new projects share the same webServer, base URL and guard.
- The doc counts (five versus seven projects) are correct where they appear.

No blockers. The two warnings share one cause. When a press on the dark area does not close the dialog, the focus trap still pulls focus to the dialog's first tabbable element (the Close button) and scrolls the backdrop to show it. The new timer exists only to hide that scroll from the close check. It works around the symptom by relying on engine timing.

## Warnings

### WR-01: A press on the dark area that does not close the dialog still moves focus out of the confirm field and scrolls the backdrop back to the top

**File:** `web/src/ui/overlays/Modal.tsx:132-140` (with `web/src/ui/overlays/useFocusTrap.ts:93-103,152-156` and `web/src/app/admin/AdminLayout.tsx:84`). Tests: `web/e2e/dialog-scrollbars.spec.ts:120-130,132-139` and `web/e2e/dialog-fit.spec.ts:201-211`.

**Issue:** The SUMMARY's own probe records the sequence: "A press on the dark area focuses `main`, and the focus trap pulls focus back to the dialog's Close button, which scrolls the backdrop." `main` is `tabIndex={-1}` in the production AdminLayout, so the same thing happens in the admin portal. The trap's `onFocusIn` calls `focusFirst()`. That focuses `tabbable(root)[0]`, the header's Close button, without `preventScroll`.

Before 02-42 this did not matter, because every press on the scrim closed the dialog. Plan 02-42 adds presses that keep the dialog open: middle, right, and a primary press followed by a scroll. Each of those still runs the browser's default focus change on mousedown.

At 1280x420, the person has wheel-scrolled the backdrop down to Cancel and Delete Order, with the order number typed. If they then right-click or middle-click the dark area:
- focus leaves the confirm field for Close;
- the backdrop jumps back to the top, and the buttons they just scrolled to go out of view.

The text is kept, so nothing is lost. But owner check step 3 ("A middle or right click on the dark area does nothing") does not hold on a scrolled backdrop. Keyboard users also lose their place: the caret is no longer in the field.

The E2E tests for these presses check only `toBeVisible()` and `toHaveValue()`, so they cannot see this. Both press from a backdrop at scrollTop 0 (T3/T4), or from one that does not scroll (1440x900).

**Fix:** Pull focus back to where it was, not to the first element, and do it without scrolling. That also removes the cause of WR-02. In `useFocusTrap.ts`:
```ts
let lastInside: HTMLElement | null = null;
const onFocusIn = (event: FocusEvent) => {
  const target = event.target;
  if (target instanceof HTMLElement && root.contains(target)) {
    lastInside = target;                      // remember where the person was
    return;
  }
  if (isTop() && target instanceof Node && !inToastLayer(root, target)) {
    if (lastInside?.isConnected === true && root.contains(lastInside)) {
      lastInside.focus({ preventScroll: true }); // it was already where the person left it
    } else {
      focusFirst();
    }
  }
};
```
Then make the E2E checks match the owner's words. In T3/T4, and in a new 1280x420 case that presses after `wheelOverDialog`, assert that `readRegion(page).scrollTop` is unchanged and that the textbox is still focused after the middle and right presses. This changes `useFocusTrap`, which every overlay uses, so it needs its own RED test (focus a field, focus `main`, and expect focus back on the field with `scrollTop` unchanged). The UI-WR-02 stack tests must stay green.

### WR-02: The "one task later" re-read relies on WebKit's timing and accepts any scroll in that window

**File:** `web/src/ui/overlays/Modal.tsx:156-172`. Tests: `web/src/ui/overlays/Modal.test.tsx:699-711` and `:714-735`, plus `web/e2e/dialog-fit.spec.ts:219-230` (D2 in webkit).

**Issue:** The fix for deviation 1 resets the press snapshot at each `focusin` and again in a `setTimeout(0)`. Two problems:

1. **It depends on task order, which nothing guarantees.** The probe found WebKit's reveal scroll "one task later". The timer works only if:
   - WebKit's reveal task runs before our `setTimeout(0)` task, and
   - both run before the `mouseup`/`click` are dispatched.

   If WebKit applies the reveal during its rendering update rather than in a plain task, a 0 ms timer usually runs first and misses it. If the mouseup and click are already queued, Chromium's scheduler runs input ahead of timers, and WebKit can do the same. Either way, a real left click on the dark area does not close the dialog. That breaks the plan's own truth: "a left click on the dark area closes … at 1280x420 … in webkit".

   The failure is safe (the dialog stays open, and a second click works because focus is already on Close). But D2 in webkit is a timing-dependent test, and it ran 8 of 8 only on an idle machine. Expect it to flake under the seven-project parallel load.
2. **It accepts real scrolls as well as focus scrolls.** Any scroll between the mousedown and the timer becomes the new baseline: wheel momentum still running, a track page-jump, or a smooth-scroll step. The comment at `:124-130` says "the scroll check covers any engine that does [send a click after a scrollbar press]". That holds only for scrolls that happen after the timer.

The unit test at `:699` ("still counts a scroll after that focus move as a scroll") blocks the close only because jsdom never runs the pending timer before the click. In a real engine, the same scroll a few milliseconds later would be accepted. So the test pins an order that real use does not guarantee.

**Fix:** Remove the cause rather than timing it. With WR-01's fix (refocus without scrolling), a press on the dark area no longer scrolls the backdrop. Then delete `onFocusIn`, `rereadPending` and the timer, and compare the mousedown snapshot with the positions at the click. Once the focus scroll is gone, also delete the "focus scroll" unit tests at `:683-735`, or invert them to assert that scrollTop stays unchanged. If the trap cannot change in this gap, at least:
- change the comment at `:124-130` to name the window in which scrolls are accepted;
- rename the test at `:699` to say it covers a scroll before the task boundary only;
- add a retry-free repeat run of D2 in webkit (`--repeat-each 25 --workers 4`) to the SUMMARY's evidence.

## Info

### IN-01: A press on the dark area that is released inside the dialog still closes it

**File:** `web/src/ui/overlays/Modal.tsx:141-155`
**Issue:** `click` fires on the nearest common ancestor of the mousedown and mouseup targets. If someone presses just outside the dialog edge, notices, and drags back in to release over the field or a button, the click's target is the scrim (`overlay`). The dialog closes and the typed order number is lost. The plan's ordering truth covers only the reverse direction (press inside, release outside), and no test covers this one. It is no worse than the old mousedown close, but under D-42 the click rule could easily protect it.
**Fix:** Also record a `mouseup` on the scrims, and close only if the mouseup's target was a scrim too, e.g. `releasedOnScrim = scrims.some((s) => s === event.target)` in a `mouseup` listener, checked in `onClick`. Add a jsdom case that runs `mouseDown(region)`, then `mouseUp(textbox)`, then `click(overlay)`, and expect it not to close.

### IN-02: The SPEC-DEVIATION comment states engine behaviour as fact that was proven only for Chromium

**File:** `web/src/ui/overlays/Modal.tsx:124-130`, `:57-61`
**Issue:** The comment says "Chromium and WebKit send no click after a scrollbar press, and the scroll check covers any engine that does". The SUMMARY's flagged assumptions say this is "proven for Chromium only (T2)". Real Safari on macOS, the most common overlay-scrollbar system, was not run. Also, the scroll check cannot cover a press-and-release without movement, because nothing scrolls.
**Fix:** Change the comment to: "Chromium is shown to send no click after a scrollbar press (dialog-scrollbars T2); WebKit and Firefox are assumed to behave the same; a press-and-release on an overlay thumb without movement is not detected by the scroll check." Add the same limit to the parity.md D-42 row or to deferred-items, so the owner can check it on a Mac if one is available.

### IN-03: The overlay project's `--enable-features` may replace Playwright's own `--enable-features`

**File:** `web/playwright.config.ts:52-57`
**Issue:** Playwright already passes `--enable-features=CDPScreenshotNewSurface` (`playwright-core/lib/coreBundle.js:34872`), and the user `args` are appended after it. Chromium keeps only the last value of a repeated switch, so the overlay project probably runs without `CDPScreenshotNewSurface`. Screenshots and failure traces in that one project would then use a different capture path from every other project. The `clientWidth === 1280` check proves overlay scrollbars are on, but it cannot detect the lost feature.
**Fix:** Pass both features in one switch, `args: ['--enable-features=CDPScreenshotNewSurface,OverlayScrollbar']`, with a comment that ties it to Playwright's default list. Or record why losing the feature does not matter for this spec.

### IN-04: A context menu does not cancel the pending press

**File:** `web/src/ui/overlays/Modal.tsx:132-155`
**Issue:** On macOS, Ctrl+click on the scrim sends `mousedown` with `button === 0` and then opens the context menu. Whether a `click` follows depends on the engine. If one does, the dialog closes behind the menu the person asked for. The jsdom test sends `contextMenu` for button 2, but nothing listens for it, so it proves nothing about this path.
**Fix:** Clear the press when a context menu opens: `scrim.addEventListener('contextmenu', () => { pendingPress = null; })` (and remove it in the cleanup). Add a jsdom case: `mouseDown(button 0, ctrlKey)`, then `contextMenu`, then `click`, and expect it not to close.

### IN-05: The right-press-then-left-click E2E steps assume no native context menu

**File:** `web/e2e/dialog-fit.spec.ts:209-212`, `web/e2e/dialog-scrollbars.spec.ts:138-143`
**Issue:** Headless Chromium, Firefox and WebKit draw no native context menu, so the left click that follows reaches the page. Run with `--headed`, `--debug` or `--ui` (how a failing run is usually investigated), and the right press may open a real menu. The next click then dismisses the menu instead of reaching the page, so the test fails for a reason that has nothing to do with the close rule.
**Fix:** Give the right press its own test, as T3 already does for the middle press, and do the left-click close in a separate test. Escape cannot be used to dismiss a menu between the two steps, because Escape also closes the dialog.

### IN-06: No E2E test taps the scrim with touch input

**File:** `web/e2e/dialog-fit.spec.ts:232-242`
**Issue:** The phone test uses `page.mouse.click` in the pixel and iphone projects, which sends mouse events directly. A real tap goes through touch, then compatibility mouse events, then `click`. In WebKit, that `click` is sent only because the scrim now has a click listener. The close trigger moved from `mousedown` to `click`, which is exactly the step that path depends on, and no test drives it.
**Fix:** Add a `locator.tap()` / `page.touchscreen.tap(x, y)` variant of the phone test (both device projects have `hasTouch`), and assert the dialog closes.

## Gap Being Closed

**G-02-2** (UAT test 2, `02-UAT.md`; diagnosis in `.planning/debug/wwwroot-vite-license-served.md`): "After a production build, the API serves only the app's files from wwwroot; build internals such as `.vite/license.md` are never served." Today `GET /.vite/license.md` answers 200 `text/markdown` with every bundled dependency and its exact version.

Root cause is an AND-gate: Vite's `build.license` writes `.vite/license.md` into the served web root, and `app.UseStaticFiles(...)` serves any file the web-root `PhysicalFileProvider` reports as existing, whose dot-prefix exclusion checks only the leaf name. This plan removes the server half (diagnosis option A): the static-file pipeline refuses dot segments, so the request falls through to the existing anonymous `{*path:file}` ProblemDetails 404. The Vite half (keep, move or drop the file; public credits) is owner decision **D-BL-04** and stays untouched.

## Planner Findings (verified 2026-10-08, scratchpad only, no repo edits)

1. **The fixture glob copies dot folders.** A scratch SDK 10.0.401 pair (library with the same `<None Include="Fixtures\webroot\**" CopyToOutputDirectory="PreserveNewest" />`, plus an app referencing it) lists `Fixtures\webroot\.vite\license.md` in `dotnet msbuild -getItem:None` and copies `Fixtures/webroot/.vite/license.md` and `.x/y.txt` into the referencing app's `bin`. The SDK's `**/.*/**` exclude applies only to the default item globs; the explicit Include has no Exclude. **No csproj change is needed.** The new theory still asserts each fixture exists under `CspsApiFactory.FixtureWebRoot`, so a future glob change cannot turn the 404 rows into vacuous passes. Neither path is git-ignored (`git check-ignore` exits 1).
2. **A slash-only dot rule is bypassable on Windows.** A scratch Kestrel host on 5116 (preflight clean; stopped afterwards) with a prototype wrapper proved: splitting on `/` only still serves `/assets%5C..%5C.vite%5Clicense.md` (Kestrel decodes `%5C` to `\`, and `PhysicalFileProvider` on Windows treats `\` as a separator) and `/VITE~1/license.md` (NTFS 8.3 short names are generated on C:; `dir /x` shows `VITE~1` for `src/Csps.Server/wwwroot/.vite`; `/INDEX~1.HTM` even serves `index.html`). Splitting on both `/` and `\` and refusing any segment that contains `~` turned every variant into a fall-through 404 while `/assets/app.js` and `/index.html` stayed 200. The production host is Windows IIS, so both rules are part of the fix, not extras.
3. **TestServer behaviour (Microsoft.AspNetCore.TestHost 10.0.12, scratch).** `System.Uri` decodes `%2E` before sending, so the in-memory `/%2Evite/license.md` row equals the plain row; the real-host curl check in Task 2 covers Kestrel's own decoding. `%5C` reaches the file provider as a backslash, and `VITE~1` resolves inside a test `bin` on C:, so both alias rows are genuinely RED on this machine before the fix. On Linux CI the uppercase, backslash and 8.3 rows pass trivially (case-sensitive file system, `\` is a file-name character, no short names); the `IsHidden` unit rows in Task 2 pin the rule on every OS.
4. **FileProvider wrapper, not middleware.** The wrapper is the narrowest seam: `StaticFileMiddleware` itself sees "file not found", calls `next`, and routing picks the existing `{*path:file}` endpoint, exactly the missing-file path that `MissingFileIsProblem404` already pins (same status, title, logging, no 401). `OnPrepareResponse = SpaCaching.Apply` and `UseResponseCompression` are untouched, so real files keep their cache headers, ETags and br/gzip. A middleware would have to either write its own 404 (bypassing the fallback endpoint) or short-circuit non-file paths such as `/.vite/` that today correctly get the shell.
5. **`/.well-known/` trade-off.** After this fix every file under a dot folder is refused, including a future deliberate `/.well-known/security.txt`, an Android App Links `/.well-known/assetlinks.json` for the planned Android app, or an ACME HTTP-01 challenge if the host ever validates certificates through the app. Today's extensionless ACME tokens are already not served by `UseStaticFiles` (unknown content type, so they fall to the shell), so this fix does not change certificate renewal; the Phase 3 first deploy records how SmarterASP.NET's Let's Encrypt validates (HOSTING-RECORD). A later need gets an explicit exact-path allow-list inside the wrapper with its own tests, never a global relaxation of the rule.

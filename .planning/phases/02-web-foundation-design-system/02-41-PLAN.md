## Gap Being Closed: G-2-199 (UAT test 199, severity major)

**Truth that failed:** "Any dialog is fully visible or scrollable in a short window (laptop at 125-150% zoom, WCAG 1.4.10), and its horizontal position matches what the owner expects."

**Root cause (from 02-UAT.md):** `overlayRegionClasses` (App. C `.s-overlay`) pins every dialog 140px below the top (row flex, top-aligned, fixed 140px top padding), its overflow is visible, `useBodyScrollLock` stops the page scrolling, and the inline dialog has no max height. At 1274x585 CSS px the Delete Order dialog runs 140..633 and its buttons end at 616: unreachable. Horizontal position is by design (centred on the window).

**Owner decision (LOCKED, 2026-10-13, recorded here as D-42; Task 3 writes it into 02-CONTEXT.md):**
1. Keep dialogs horizontally centred on the whole window. No change.
2. On a short window, move the dialog up so the whole dialog is visible: the 140px top gap shrinks as needed, down to the normal 16px edge gap. Tall windows keep the approved 140px position pixel-for-pixel.
3. If the window is too short even with a 16px gap, the backdrop scrolls so every part of the dialog is reachable (WCAG 1.4.10).
4. The phone bottom-sheet layout is unchanged unless it has the same defect.

**Phone check (done while planning, read-only, headless Chromium against this project's own dev server on 5180, Delete Order dialog opened from /dev/components):**

| Window | Sheet / dialog top..bottom | Delete Order button bottom | Fits? |
|---|---|---|---|
| 1440x900 desktop | 140..633 | 616 | yes |
| 1274x585 desktop | 140..633 | 616 | **no** |
| 1280x420 desktop | 140..633 | 616 | **no** |
| 412x839 phone (Pixel 7) | 96..677 | 660 | yes |
| 393x659 phone (iPhone 15) | 96..697 | 680 | **no** |
| 320x568 phone | 96..776 | 759 | **no** |
| 659x393 phone landscape | 96..635 | 618 | **no** |

The phone sheet **has the same defect**, so under decision point 4 it is in scope. It gets the same rule with App. C's phone values: the 96px gap shrinks as needed down to the phone's normal edge gap, which is 0 (App. C phone `.s-overlay { padding: 96px 0 0 }` has no side or bottom gap), and then the backdrop scrolls. Wherever the sheet already fits (412x839, and the 900px-tall parity rows) nothing moves.

**Design (pure CSS, chosen per the orchestrator's preference; no JS measuring, no inline style):** the region becomes a column flex box with 16px padding (0 on phone pages). Its `::before` pseudo-element is a spacer with `flex: 0 1 124px` (96px on phone pages) above the dialog, so padding + spacer equals the approved 140px (96px) whenever the dialog fits. When it does not fit, only the spacer can shrink, down to 0. The direct children never shrink (App. C sets the inline overlay's `min-height: 0`, so in a column it would otherwise be squashed). `justify-content: flex-start` keeps any overflow at the bottom, where it can be scrolled to; a centred column would push the top out of reach. `overflow-y: auto` makes the backdrop scroll as the last resort. Horizontal centring stays (`align-items: center`, and the child is full width). A pseudo-element, not a new `<div>`, keeps every DOM path the approved one, so the parity pairing needs no structural exception: both sides draw the same `::before`, which `web/visual/compare.ts` already walks and compares.

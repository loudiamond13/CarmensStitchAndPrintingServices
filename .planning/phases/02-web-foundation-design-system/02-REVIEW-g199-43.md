## Summary

Plan 02-43 replaces the 02-42 workaround for WR-01/WR-02 with a root-cause fix. `useFocusTrap` now remembers the element inside the dialog that last had focus (`lastInside`, seeded after the initial focus) and returns stray focus to it with `focus({ preventScroll: true })`. `Modal` drops its `focusin` re-read and the `setTimeout(…, 0)` window, so any scroll between the press and the click blocks the scrim close. The e2e side adds scrolled-backdrop cases for middle and right presses and a phone-screen right-press case.

Checked and found sound:
- The trap's `lastInside` bookkeeping. It is seeded after the initial focus. A focus-in inside the root is recorded for every trap, the top one or not. Only the top trap returns focus. The `isConnected`, `root.contains` and `document.activeElement === lastInside` checks cover an element that is gone, moved or disabled, and `focusFirst()` is the fallback. `SVGElement` is handled. A re-entrant `focusin` from the `focus()` call lands in the record branch, so it cannot loop.
- Modal's removal of the `focusin` listener, the timer and the `clearTimeout`. Nothing is left over in the cleanup.
- The Firefox exception. It is `button === 'middle' && testInfo.project.name === 'firefox'`, and the project is named `firefox` in `playwright.config.ts`. It is not wider than Firefox plus the middle button, so it matches the owner's 2026-10-14 decision. I do not flag it.
- ESLint is clean on all 8 files, and `vitest run src/ui/overlays` passes (119 tests). I could not run Playwright here.

The remaining defects are a fallback path in the trap that can still scroll the backdrop and block the close, and a docs row that states a rule the tests contradict. There are also minor quality items.

## Warnings

### WR-01: The `focusFirst()` fallback in `returnInside` still scrolls the backdrop, so WR-01 and WR-02 survive on that path

**File:** `web/src/ui/overlays/useFocusTrap.ts:133-141` (and `web/src/ui/overlays/Modal.tsx:131-133`)
**Issue:** `returnInside` goes through `preventScroll` only when `lastInside` is still connected, inside the root and able to take focus. In every other case it calls `focusFirst()`, whose `target.focus()` and `root.focus()` calls scroll normally. That case is not exotic:
- The confirm button was focused and then became disabled (the Delete Order button when a save or delete starts, or when the text no longer matches). The unit test `falls back … can no longer take focus` covers this very case.
- The focused element was unmounted, for example in a multi-step dialog.
- The initial focus target was disabled, so `lastInside` is `null`.

A press on the dark area of a scrolled backdrop in these states focuses `main`. The trap then runs `focusFirst()`, and the browser scrolls the first field into view. That is the backdrop jump of 02-REVIEW-g199-42 WR-01. Modal's new rule is "any scroll between the press and the click is a scroll gesture", so a left click that follows (a click on the dark area after a press that focused `main`) is silently ignored. That is the WR-02 symptom, and without the old re-read and timing window nothing compensates for it. In WebKit the reveal may arrive a task after the focus move, which is the case the removed `setTimeout` covered. The Modal header comment says focus "comes back … without scrolling", which is not true on this path. No test covers the interaction between this path and the scrim close.
**Fix:** Do not scroll when focus returns because of a pointer press. Make the fallback non-scrolling as well, and keep the scroll-into-view only for the keyboard path, which is not the one that arrives through `focusin` from outside:

```ts
const focusFirst = (options?: FocusOptions) => {
  const target = tabbable(root)[0];
  if (target !== undefined) {
    target.focus(options);
    return;
  }
  if (!root.hasAttribute('tabindex')) root.tabIndex = -1;
  root.focus(options);
};
// in returnInside:
focusFirst({ preventScroll: true });
```

Add a Modal-level test with a real `main`: the confirm button disabled, a right press and then a left click on the dark area, expecting no scroll and the close to still work.

### WR-02: `docs/web/e2e.md` says a drag on the scrollbar leaves scrollTop unchanged, but the test asserts that it scrolls

**File:** `docs/web/e2e.md:115`
**Issue:** The new `@dialog-fit` row says that "a press or drag on the backdrop's scrollbar keep the caret in the confirm field and the backdrop's scrollTop unchanged". In `web/e2e/dialog-scrollbars.spec.ts:122` the drag test asserts the opposite: `expect(after, 'the drag scrolled the backdrop').toBeGreaterThan(before)`. Only the press without movement (`:136`, `:112`) is asserted unchanged. The release-gate page is the pass rule people read, so it now describes a check that does not exist for a drag and contradicts the one that does. The same row also states "the backdrop's scrollTop unchanged" for the middle and right press without saying it is asserted for the classic and overlay Chromium projects separately from the engine projects. This blurs which project proves what.
**Fix:** Reword to what the tests do: "a press on the backdrop's scrollbar keeps the caret and leaves scrollTop unchanged; a drag on it scrolls the backdrop and keeps the dialog open with the typed text and the caret; a middle or right press on the dark area keeps the caret and scrollTop (Firefox's own middle-button scroll is the one documented exception)".

## Info

### IN-01: The caret position `13` is a magic number repeated in five places

**File:** `web/e2e/dialog-fit.spec.ts:290`, `web/e2e/dialog-fit.spec.ts:337`, `web/e2e/dialog-scrollbars.spec.ts:94`
**Issue:** `{ start: 13, end: 13 }` is the length of `ORDER` (`ORD-2026-0148`). If the sample order number changes, the assertion fails with a confusing diff, and it hides what it means.
**Fix:** Use `{ start: ORDER.length, end: ORDER.length }`, or add a small `expectCaretAtEnd(page)` helper next to `readCaret` in `deleteOrderDialog.ts`.

### IN-02: `revealScrollbar` duplicates the new `waitForSettledScroll` helper

**File:** `web/e2e/dialog-scrollbars.spec.ts:60-71`
**Issue:** The poll loop (`last`, `settled = now > 0 && now === last`, `intervals: [100]`) is a copy of `waitForSettledScroll` in `deleteOrderDialog.ts:90-106`, which this same plan added. Only the message differs.
**Fix:** After the wheel, call `await waitForSettledScroll(page);` and drop the local loop.

### IN-03: The WR-02 Modal tests keep fake-timer machinery that no longer tests anything

**File:** `web/src/ui/overlays/Modal.test.tsx:712-731`, and the overlap with `:685-710`
**Issue:** The `setTimeout` window was removed from `Modal`, so `vi.useFakeTimers()`, `vi.advanceTimersByTime(0)` and the try/finally restore in `counts a scroll a task after a focus move…` do nothing. The test is also the same assertion as `still counts a scroll after that focus move` (`:699`) and `counts a scroll during the press…` (`:685`): scroll after the press means no close. Three tests give the impression of three behaviours. They also fire `focusIn` on the Close button, but Modal no longer listens to `focusin`, so that line is a leftover too.
**Fix:** Keep one test for "any scroll between the press and the click blocks the close", drop the fake timers and the `focusIn` calls, and keep the scroll-then-restore-to-the-start case if it is meant to be a distinct case (a scroll that returns to the starting value compares equal, which is accepted).

### IN-04: "Every trap records … the top one or not" has no test that would fail if the recording were gated

**File:** `web/src/ui/overlays/useFocusTrap.ts:180-184`, `web/src/ui/overlays/useFocusTrap.test.tsx` (stacked-trap tests)
**Issue:** The comment makes a rule: a trap below the top still tracks its own focus. The stacked-trap tests only check the top trap's return (`:361-363`). Moving the `lastInside = target` line below the `isTop()` check would pass the whole suite.
**Fix:** Add a test: with two traps open, focus moves inside the lower trap and then the upper trap ends. The lower trap's last element should be the one that regains focus when the trigger is gone, or drop the "top one or not" claim from the comment if the recording does not matter.

## Decisions Made

- The license exception is version-pinned in its own file instead of being an allow-listed license. Widening `allowed-licenses.json` with "Microsoft Software License Terms" would have let any Microsoft-licensed package in.
- The approval goes under `approvals` in `docs/dependencies.json`, not `policy.exceptions`. That field is scope-wide and is validated per registry entry, and the two packages are transitive, so they have no registry entries.
- Stale exceptions fail the gate. An upgrade forces a fresh owner approval rather than leaving a dead pin behind.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 - Missing Critical] Coverage gate fails when ReportGenerator's filter matches nothing**
- **Found during:** Task 1
- **Issue:** ReportGenerator exits 0 when its assembly filter matches nothing, so a renamed assembly would silently pass.
- **Fix:** The gate re-reads `Summary.json` and fails when the expected assembly is missing or has no coverable lines.
- **Committed in:** `71f7938`

**2. [Rule 1 - Bug] Null-safe validation-error counting in the license script**
- **Found during:** Task 2
- **Issue:** In PowerShell, `@($null).Count` is 1, so a package with no `ValidationErrors` field would have been counted as failing.
- **Fix:** Added a `Get-ValidationErrors` helper that always returns an array. JSON arrays are also enumerated explicitly, so Windows PowerShell 5.1 and pwsh agree.
- **Committed in:** `be59f66`

**3. [Rule 2 - Missing Critical] Exceptions-file validation and stale-entry detection**
- **Found during:** Task 2
- **Issue:** An exceptions list needs guards, or it can widen silently through a range or wildcard version, a duplicate, or an entry that outlives an upgrade.
- **Fix:** The script validates each entry (exact version regex, yyyy-MM-dd approval date, https license link, required fields, no duplicates). It also fails on any exception that matches no failing package.
- **Committed in:** `be59f66`

**4. [Rule 2 - Missing Critical] Documented the compatibility-level step**
- **Found during:** Task 3 (clean-clone proof)
- **Issue:** `dotnet ef database update` creates a new database at the SQL Server 2025 default (170). Only the dev seed pins it to 160 (D-13), so a developer who stops after migrating would be on a different level.
- **Fix:** Added a note to `docs/development.md` step 4 to always run the seed after creating a database.
- **Committed in:** `03aa31c`

**Planned checkpoint, not a deviation:** Task 2 stopped at the D-00/D-18 stop-and-ask rule for the two Microsoft-licensed packages. The owner chose Option A on 2026-10-07, as recorded above.

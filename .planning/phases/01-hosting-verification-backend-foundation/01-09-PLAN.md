<task type="checkpoint:decision" gate="blocking">
  <name>Task 1: Owner confirms the append-only design and the retention purge path (D-25, one-way door)</name>
  <decision>How the AuditLog table blocks changes, and whether the 2-year retention purge (hardening phase) gets a built-in, narrow exception now.</decision>
  <context>D-25 (owner): append-only, UPDATE and DELETE blocked at the database level, 2-year retention, purge job in the hardening phase, and "design how the future purge legitimately bypasses it". This is a one-way door: once real audit rows exist, loosening the guarantee later undermines the log's value as evidence. On shared hosting the app login is probably db_owner, so permission DENYs would not stop it; research verified a trigger approach instead. Residual risk in every option (accept or reject): a db_owner can still disable the trigger or drop the guard table on purpose. The protection stops application bugs and injected statements, not a malicious database administrator. Plan 09 also adds a test that the trigger exists and is enabled; a runtime check can join /health or a maintenance job in the hardening phase.</context>
  <options>
    <option id="option-a">
      <name>Trigger with a narrow, built-in purge path (recommended)</name>
      <pros>AFTER UPDATE, DELETE trigger raises error 51000 on any UPDATE and 51001 on any DELETE, except a DELETE where the session flag csps.audit_purge = 1 is set AND every deleted row is older than 2 years. An empty AuditLogTruncateGuard table with a foreign key makes TRUNCATE fail. The hardening-phase purge works without ever touching the trigger, and even the purge can never delete a row younger than 2 years.</pros>
      <cons>Anyone with database access who learns the flag name can delete rows older than 2 years (which retention allows anyway).</cons>
    </option>
    <option id="option-b">
      <name>Strict trigger with no purge path</name>
      <pros>No DELETE of any row is ever accepted; the simplest possible guarantee.</pros>
      <cons>The 2-year retention purge in the hardening phase must ship a reviewed migration that changes the trigger, which reopens this one-way door at that time.</cons>
    </option>
  </options>
  <resume-signal>Reply "option-a" or "option-b" (or describe a different rule; the executor then stops for re-planning).</resume-signal>

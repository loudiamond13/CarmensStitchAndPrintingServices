### W2 Update banner (PERF-06, D-14)

**When it shows:** the worker finds a new version after a deploy and it is waiting. The app checks for a new version when it opens, and again when it comes back to the front, at most once an hour (accepted working default, 14 D-33; checked at the owner's UI review). The app **never reloads by itself** (D-14).

**Where:**
- **Admin shell:** a full-width strip in the main column, directly under the Topbar and above `main#main`. It scrolls with the page (not sticky), so it never covers a control, a sticky save bar, a toast or the tab bar. Each page change scrolls to the top, so it is seen on every new page.
- **Sign-in screens:** a full-width strip as the first child of the AuthLayout page root, above the AuthFrame.
- Not on the offline screen (W3) and never on public pages.

**Anatomy (one row, `pwa.recipe.ts`):** `flex items-center`, `--info-soft` ground, 1px bottom border (§ Color), padding 12px top and bottom and 32px sides (24px on tablets, 16px on phones), then:
1. the `info` icon, 20px, `--info`, hidden from assistive technology;
2. a text block (`flex-1 min-w-0 wrap-anywhere`): the message `<p>` "A new version is available." (Label: 14/20, 600, `--ink`), then the save hint `<p>` "Save your work first, then reload." (Small: 14/20, 400, `--ink`) *(OQ-3, 14 D-27)*;
3. the "Reload" Button, `secondary md` (44px), `shrink-0`, at the end of the row.

**Focal point:** the message, then the Reload button.

**Behavior:**
- **Stays** until Reload is pressed or the app is next opened (D-14). There is no close button. Moving between pages, and between sign-in and the shell, keeps it (one store, § Component Inventory).
- **Reload:** the button goes pending ("Reloading", spinner, ignores more presses); the waiting version takes over and the page reloads once. If the page has an unsaved-changes guard, the browser's own leave prompt shows first; if the person stays, or the page is still there 5 seconds after the press, the button returns to "Reload" and the banner stays.
- **Several tabs or windows:** Reload in one updates the worker for all; a Reload in another tab where nothing is waiting any more simply reloads that tab.
- **Next open:** when every app window was closed, the new version is already active on the next open, so no banner shows.

**Announcements and focus:**
- The banner renders inside an always-mounted `div aria-live="polite"` (zero size when empty, the ToastProvider pattern; no role, so it is not read twice). When the banner appears, screen readers read "A new version is available.", the save hint and the button once. It is polite, not an alert: an update is not urgent.
- The banner is a `<section aria-labelledby>` named by its message, so it is a findable region.
- **It never takes focus**, so typing is never interrupted. Keyboard order: skip link, sidebar, Topbar, banner, `main`. The skip link still goes straight to `main`.
- Motion: it appears with `animate-csp-fade` (0.15s, existing token) and `motion-reduce:animate-none`.

### W3 Offline screen (PERF-06, D-15)

**When it shows:** an `/admin/*` document opens (or reloads) with no connection: the device reports offline (`navigator.onLine === false`), or the first session check gets **no answer at all**. It shows in place of the asked route, including the sign-in page (whose loader otherwise opens the form even when the check fails). It is the installed app's offline page, and the same rule applies to an admin tab in a browser once the worker is installed.

**When it does not show:**
- When the signal drops while the app is already open: each action keeps today's messages ("Check your internet connection...") and every form keeps what was typed *(OQ-2, 14 D-29)*.
- When the server answers with any status (a 5xx shows the existing admin error screen).
- On public pages (no worker there; the browser's own offline page shows).

**Anatomy:** the AuthFrame (Blush, brand panel and form column, P4; owner ruling 14 D-32: the sign-in card look, not a bare page), with one card in `main#main` (`loginCardClasses`):
1. AuthHeader: eyebrow "CSPS Admin" (existing `AUTH_COPY.eyebrow`), h1 "You're offline" (`tabIndex={-1}`), subline "Orders and payments need a connection. Try again when you have signal."
2. Button `primary lg block` "Try Again".
3. A status line `<p role="status">` (Small, `--ink-muted`), empty until a retry fails.

No icon, no picture, no data. Nothing is stored on the device (D-15).

**Focal point:** the h1 "You're offline", then the "Try Again" button.

**Behavior:**
- On show, focus moves to the h1 (the `ResetInvalidCard` pattern), so a screen reader reads the heading first.
- **Try Again:** the button goes pending ("Checking") and runs the session check again.
  - Answer received: the asked route opens (the sign-in form, or the page with a live session), with that page's own focus rule.
  - Still no answer: the button returns to "Try Again" and keeps focus; the status line says "Still no signal. Check your mobile data or Wi-Fi, then try again." (read politely).
- No automatic retry: the screen waits for Try Again (accepted working default, 14 D-33; checked at the owner's UI review).

### W4 View Transitions and reduced motion (PERF-07; Claude's discretion for the style)

**Look:** the browser's own cross-fade of the whole page, **0.25s** (the default the browser applies to the root). No element is given its own transition name, and no CSS is added, so the stylesheet contract stays as it is and the timing cannot drift. Parts that are the same on both pages (header, sidebar, Topbar, tab bar) look still, because a cross-fade between identical pixels shows nothing; only the changed content fades. 0.25s sits inside the 150 to 250 ms range P2 D-38 set for exit motion.

**Where it applies:** a page-to-page navigation started by the person, in both areas:
- **Public:** links between Home, Products, Gallery, Contact, Privacy, Terms, Accessibility and the not-found page (header nav, footer links, Get a Quote links to `/contact`, Staff Login).
- **Admin:** sidebar and tab bar items, links and buttons that open another page (a list row to its record, back links, Open Order, View Request), the sign-in steps, a page change after an action (for example save, then the new order's page), and sign out.

**Where it does not apply:**
- URL-state changes on the same page: filters, search, pagination, page size, sort, tabs, the Gallery photo viewer address (WEB-10, nuqs);
- `#` links, dialogs, the lightbox, slide-overs and menus (their own P2 motion);
- links inside the phone drawers (admin MobileNavDrawer, public site menu): the drawer's own exit motion is the change, so those links pass `noTransition`;
- browser Back and Forward, loader redirects, the first load and full reloads;
- browsers without View Transitions: the page changes at once, as today.

**Reduced motion:** with `prefers-reduced-motion: reduce`, no View Transition starts at all (UiLink and the programmatic navigations read `usePrefersReducedMotion`; a change to the device setting applies at once).

**Timing and input:** the transition starts only once the new page is ready (its chunk and loader), so the old page stays until then and nothing flashes blank; the admin skeleton page head still shows in `main` while a chunk loads, as today. During the 0.25s the page takes no clicks (browser behavior).

**Focus, titles, announcements:** unchanged. The transition is visual only; the existing focus and document-title rules run after the swap.

**CLS, CSP, bundle:** the cross-fade is drawn over the page and moves no layout, so CLS stays under 0.05; Lighthouse and the CLS gate re-run (D-05). No inline style or script. The public bundle grows only by the UiLink change and the small hook; the budget gate measures it (the Privacy row has well under 1 KB left).

**Reduced-motion audit (PERF-07 "all motion is disabled"):** Phase 14 lists every animation, transition and smooth scroll in `web/src` and proves each stops under reduced motion:
- transitions: the existing `base.css` rule (`transition-duration: 0s !important`);
- animations: `motion-reduce:animate-none` on each recipe (dialogs, drawers, toasts, shimmer, site menu, burger, banner);
- smooth scroll (for example Tabs, the Contact "Get a Quote" scroll): `behavior: 'auto'` under reduced motion;
- View Transitions: never started;
- the pending spinner: keeps its slow 2.4s turn *(OQ-4, 14 D-30)*; every other motion stops.

## Fixed Issues

### WR-G1-01: One address can use up the whole site-wide ceiling

**Files modified:** `src/Csps.Server/Security/RateLimitingRegistration.cs`, `tests/Csps.Server.IntegrationTests/RateLimiting/AnalyticsRateLimitTests.cs`
**Commits:** `eaff4c31` (test first), `a3dada08` (fix)
**Status:** fixed: requires human verification (it is a logic change; the new test and the existing limiter tests pass).
**Applied fix:**
- Red first: new test `APageViewRefusedPerAddressDoesNotUseUpTheSiteWideCeiling` sets the per-address limit to 2 and the ceiling to 5, sends 6 views from one address (2 get 204, 4 get 429), then one view from a second address. It failed with 429 for the second address, which is the bug.
- Fix: the global limiter is now `PartitionedRateLimiter.CreateChained(CreatePageViewAddressLimiter(collect), CreateSiteWideLimiter(ceiling))`. The first link is the same per-address window as the `analytics-collect` policy (same key, same options), for the page view route only. A call refused per address never reaches the ceiling. The ceiling stays 600 a minute and the per-address limit stays 120 a minute; no setting changed.
- The window options moved into one `WindowOptions` helper and the page view check into `IsPageView`, so the three limiters share one definition. The `[EnableRateLimiting]` attribute and the 429 body logic are unchanged.
- Green: the new test passes, and the whole `RateLimiting` namespace passes (86 tests).
- Known detail: the per-address window now exists twice (the chain link and the attribute policy). Both count the same calls, so the limit is still 120 a minute for one address.

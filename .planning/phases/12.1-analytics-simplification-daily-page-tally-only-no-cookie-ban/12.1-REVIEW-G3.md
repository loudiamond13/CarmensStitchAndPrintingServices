# Phase 12.1: Code Review Report, G3 (tests, e2e, scripts and tooling)

## Summary

The removal gates are mostly real. I checked each one against "does it fail if the removed thing comes back":

- **Removed routes.** `RemovedAnalyticsRoutesTests` posts to the three old routes with the CSRF header and expects 404. If a route returned in any form (204, 400, 401, 403) it fails.
- **Retired cookies.** `RetiredCookiesTests` checks name, path, SameSite, HttpOnly, Secure, no Domain and an expiry in the past. It also checks that other cookies are never touched. The e2e `@no-cookies` case uses literal cookie names, so a wrong constant is still caught there.
- **No cookies at all.** The e2e `context.cookies()` must equal `[]` on Home and Gallery, in both a plain and a GPC browser.
- **Consent code and `web-vitals`.** `no-consent.node.test.ts` checks that files are gone, that nothing imports them, that the CSS token is gone, and that `web-vitals` is absent from `package.json` and the lock file.
- **Retired page, cookie names and shared fixtures.**
  - The `/cookies` page answers 404 with no redirect at server level (`ShellHeadTests`), in the router, and in the e2e sweep.
  - The Privacy Policy cookie list is checked against the C# cookie constants, and retired names are excluded.
  - Server and web both read `page-names.json`, `legal-pages.json` and `public-paths.json`.
- **Retention job.** `AnalyticsRetentionJobTests` proves that no roll-up is attempted: a forced failure on `DailyReferrerCounts` still removes the raw rows, and the device and source tables stay empty.
- **Secrets and paths.** I found no real secrets, emails, server names, `C:/Users/...` paths or long dashes in the added lines. Fake values use `example.test`.
- **Testing-only seed.** `/api/testing/analytics` tests are guarded by `BuildFlavor.HasTestingFeatures`.

Per-decision coverage is good. D-63, D-65, D-67, D-69, D-70, D-72, D-74, D-76 and D-77 each have a test.

There are no blockers. The three warnings are one e2e test that will flake on the shared database, and two sitemap and shell-head tests that cannot fail for the thing they are named after.

## Warnings

### WR-G3-01: e2e "sees each count rise" test depends on each page being inside the top 5 of a shared, growing database

**File:** `web/e2e/visitor-stats.spec.ts:162-181`

**Issue:** The test reads the row for Home, Products and Gallery from the "Most viewed pages" list before and after a visit. `listCount` (lines 76-85) returns `0` when the row is absent. The list now shows only the top 5 (D-67).

- `CSPS_E2E` is shared by five browser projects and every public spec.
- The database accumulates over the default last-30-days range.
- There are 8 page keys, and the privacy, terms, accessibility and not-found pages are hit heavily by `public-sweep` (8 widths times 5 projects).
- So Products or Gallery can sit at rank 6 or lower. If a page is outside the top 5 both before and after, `listCount` returns 0 both times, and `toBeGreaterThanOrEqual(before + 1)` fails. This is a flake that cannot be fixed by retrying.
- When a page is in the top 5 before and after, the assertion is sound. The risk is only the rank boundary.
- This is the project's main "a Manager sees the visits" proof, so the flake would be expensive.

**Fix:** Assert on something the top 5 cannot hide.

- Compare the `Page views` KPI before and after, with at least `+3` (the existing "at least" rule for shared counts).
- Keep the per-page check only for a page that is seeded to rank high. For example, seed a large count for `home` and `gallery` through `seedAnalytics` on a recent day, then read it.

```ts
const totalBefore = await kpiCount(manager, 'Page views');
// ...open the three pages...
await openStats(manager);
expect(await kpiCount(manager, 'Page views')).toBeGreaterThanOrEqual(totalBefore + 3);
```

### WR-G3-02: `TheSitemapNeverListsTheOldCookiePolicyPath` cannot fail, and the other sitemap and head tests derive their expected values from the code under test

**File:** `tests/Csps.Server.IntegrationTests/Http/SeoEndpointTests.cs:79-88`, also lines 62, 114, 128 and `tests/Csps.Server.IntegrationTests/Http/ShellHeadTests.cs:927-940`

**Issue:**

- The "never lists /cookies" test builds a factory with a stub `ApprovedLegalPages("/privacy", "/terms", "/accessibility")`. A stub that does not approve `/cookies` means the sitemap cannot list it, whatever the real route table or `LegalPages.All` hold. The stub hides the regression the test is named for.
- The sitemap assertions at lines 62, 114 and 128 now compute the expected URLs from `LegalPages.All.Where(Approved)`. They therefore follow the production fact: if `/cookies` came back as an approved page, expected and actual would both include it, and the test would pass.
- The robots-meta check in `ShellHeadTests` (`ALegalPageSendsItsTitleAndLeadAndItsRobotsMetaFollowsItsApprovedFact`) uses `LegalPages.ByPath(path).Approved` the same way. The draft state of the Privacy Policy is no longer pinned there.
- Real protection exists, but only elsewhere. `LegalPagesTests` plus the shared `legal-pages.json`, and `PublicRouteTableTests`, fail if `/cookies` returns or the privacy page flips approval.
- So these tests are not wrong, but they no longer guard the sitemap or head on their own. That weakens the removal gate the owner asked for (D-72, `/cookies` is a plain 404 and is not in the sitemap).

**Fix:**

- Make the "never lists" test hit the real routing path: approve every path including `/cookies` in the stub, then assert it is still absent. That proves the route table, not the catalog, excludes it.
- Keep one sitemap test with a literal expected list for the default factory, so a change to the Domain facts shows up as a visible test edit.

```csharp
await using var factory = new ShellTestFactory(
    new StubPublicContentReader("Sample Shop"),
    new ApprovedLegalPages("/privacy", "/terms", "/accessibility", "/cookies"));
// ...
body.ShouldNotContain($"{Origin}/cookies", Case.Sensitive);
```

### WR-G3-03: "no cookie bar" component test passes if the page renders nothing useful, and costs 250 ms each time

**File:** `web/src/layouts/PublicLayout.test.tsx:299-305, 310-321`

**Issue:** `expectNoCookieBar()` is `findByRole(..., { timeout: 250 }).rejects.toThrow()`.

- It passes on any failure to find the region. That includes a layout that crashed into an error boundary.
- In "shows no cookie bar on a first visit" nothing positive is asserted after `renderAt`, so a blank or crashed layout is also green.
- The "adds no bar padding" check asserts that a class does not contain `--spacing-consent-bar`. That token no longer exists in `app.css` (`no-consent.node.test.ts` proves it), so the check is trivially true.
- Time cost: the three uses add about 750 ms of real waiting. Under the heavy parallel load the suite runs in, a fixed 250 ms timeout is also the kind of timing the owner is fighting. A bar that appears late would still be missed.

**Fix:** After `renderAt`, assert a positive landmark (the header, or the page `h1`), then check absence synchronously with `queryByRole`. The lazy consent slot no longer exists, so no waiting is needed.

```ts
await renderAt('/products');
expect(screen.getByRole('banner')).toBeInTheDocument();
expect(screen.queryByRole('region', { name: 'Cookie choices' })).not.toBeInTheDocument();
```

## Info

### IN-G3-01: Retired cookie tests use the same constant for setup and assertion

**File:** `tests/Csps.Server.IntegrationTests/Analytics/RetiredCookiesTests.cs:23, 37, 51, 97, 105`

The tests build the request cookie from `RetiredCookies.ConsentCookieName` and `VisitorCookieName`, and assert the answer with the same constants. If a constant were mistyped, so that it no longer matched the real Phase 12 name, the .NET tests would still pass. The e2e `@no-cookies` case uses the true literals (`__Host-csps_consent`, `__Secure-csps_vid`), so the real check exists, but only when e2e runs. `PageViewCollectTests` already hard-codes `__Secure-csps_vid`.

**Fix:** Add one small test that pins the two constants to the literal strings.

### IN-G3-02: `AnalyticsSurfaceTests` guards removal by type name only

**File:** `tests/Csps.Application.UnitTests/Analytics/AnalyticsSurfaceTests.cs:9-80`

It lists 14 removed type names plus a few more. A reintroduced consent handler under a new name passes this test. The route test (`RemovedAnalyticsRoutesTests`) and the `CollectPageViewHandler` constructor test (`CollectPageViewHandlerTests.cs:31-33`) cover the behavior. The constructor-parameter-name assertion is also brittle, because any new parameter forces a test edit.

**Fix:** Optional. A broader guard is to assert that no type in the Application assembly has `Consent`, `Vital`, `Visitor` and `Salt` in its name apart from an explicit allow-list.

### IN-G3-03: The 121-request rate limit test could straddle a window under heavy load

**File:** `tests/Csps.Server.IntegrationTests/RateLimiting/AnalyticsRateLimitTests.cs:46-68`

It sends 121 sequential requests, each with a database write, against a 1-minute window. On an overloaded shared LocalDB it is possible, though unlikely, for the run to cross a window boundary. The 121st request would then be allowed and the test would fail without any real defect.

**Fix:** Set the window to a long value through configuration for this test, which `AnalyticsCollectRateLimit` supports (`RateLimits:AnalyticsCollect:Window`). Keep the 60-second bound on `Retry-After` in a separate short test.

### IN-G3-04: Dev scenario data still names referrers

**File:** `web/src/dev/scenarios/groups/visitor-stats.ts:57-69`

The ranked rows were renamed `RANKED_ROWS`, but the rows are still `facebook.com`, `google.com`, `Direct`, and so on. The "Most viewed pages" list now shows page names, and referrers are gone from the product. The showcase therefore displays data that cannot occur.

**Fix:** Use the page names from `tests/fixtures/page-names.json` (Home, Gallery, Products, and so on).

### IN-G3-05: Stale wording and names left behind

**File:** `web/e2e/visitor-stats.spec.ts:~179` (comment "the sweep and consent specs hold it"), `tests/Csps.Infrastructure.IntegrationTests/Analytics/VisitorStatsReaderTests.cs:12` (`Cut`, "old visit cut"), `web/e2e/no-cookies.spec.ts:8` (`SPEED_READER` chunk-name regex)

The consent specs no longer exist, so the comment misleads. `Cut` is the removed 13-month visit cut and now only labels a date. The e2e speed reader check matches only a chunk named `speedReport-*.js`, so a speed reader under another name passes it. The `web-vitals` check in `no-consent.node.test.ts` covers that case.

**Fix:** Reword the comment, rename `Cut` to say what it is, and keep the e2e check as a cheap extra guard only.

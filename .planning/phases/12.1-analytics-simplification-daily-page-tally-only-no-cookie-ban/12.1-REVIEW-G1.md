## Warnings

### WR-G1-01: One address can use up the whole site-wide ceiling and stop every other visitor being counted

**File:** `src/Csps.Server/Security/RateLimitingRegistration.cs:83` (and the limiter at 133-149)

**Issue:**
- D-74 adds the ceiling as `options.GlobalLimiter`.
- ASP.NET Core's rate limiter takes the global lease first, then the endpoint (per-address) lease.
- Sliding-window permits are not given back when the endpoint limiter then refuses the request.
- So a request the per-address `analytics-collect` rule rejects (120 a minute) still uses one of the 600 ceiling permits.
- One address, or a few, sending about 600 or more beacons a minute (each needs only a browser-like User-Agent and the CSRF header) leaves the ceiling empty.
- Every real visitor's beacon then gets 429, and the client ignores it, so the page tally silently drops views.
- The per-address limit is meant to stop one address from hurting the counts (T-12-28). In this order it does not.

**Fix:** Take the per-address lease before the site-wide one by chaining them in the global limiter, so a request refused per address never reaches the ceiling:

```csharp
options.GlobalLimiter = PartitionedRateLimiter.CreateChained(
    CreatePerAddressBeaconLimiter(collect),   // same partition key and options as AddPolicy, beacon route only, else GetNoLimiter
    CreateSiteWideLimiter(ceiling));
```

This keeps the `[EnableRateLimiting]` attribute usable for the 429 body (`policy`), or drop the attribute from the beacon and keep one source of truth. Add an integration test that sends more than the per-address limit from one address and then proves a second address is still accepted.

## Info

### IN-G1-01: Stale API doc on the visitor stats read promises figures that no longer exist

**File:** `src/Csps.Server/Controllers/VisitorStatsController.cs:26-30` (also `:11`)

**Issue:**
- The `Get` summary still says it "Reads unique visitors, visits and page views" and that visits and unique visitors are kept 13 months and "answered as null".
- `VisitorStatsResponse` now has only page views, the trend and the top pages (D-57, D-70).

**Fix:** Say "Reads total page views, the trend (per day up to 62 days, else per month) and the 5 most viewed pages for a date range. Daily page counts are kept 3 years." Drop the 13-month and null sentences.

### IN-G1-02: The 429 text for the site-wide ceiling says "from this address"

**File:** `src/Csps.Server/Security/RateLimitingRegistration.cs:21,178-182`

**Issue:**
- When the ceiling refuses a call, `OnRejected` finds the `analytics-collect` policy and answers `AttemptsDetail`: "Too many attempts from this address."
- For the ceiling that is untrue, because the limit is site-wide.
- The beacon client ignores the body, so the impact is small, but the plain-English error rule applies.

**Fix:** Use a neutral line such as "Too many requests right now. Please wait and try again." for the analytics policy, or distinguish the ceiling lease.

### IN-G1-03: The ceiling is tied to the endpoint name string "RecordPageView"

**File:** `src/Csps.Server/Security/RateLimitingRegistration.cs:22,136-137`; `src/Csps.Server/Controllers/AnalyticsController.cs:33`

**Issue:**
- The site-wide limit applies only when the endpoint name equals the literal `"RecordPageView"`, a copy of the `[EndpointName]` value.
- Renaming the action or attribute silently turns the ceiling off. The compiler cannot see it.
- Only a test would notice.

**Fix:** Share one constant (for example `AnalyticsController.PageViewEndpointName`) or match on `EnableRateLimitingAttribute.PolicyName == RateLimitPolicies.AnalyticsCollect`. Keep the integration test that proves the ceiling trips.

### IN-G1-04: Retention doc comments swap D-04 and D-05, and `SaltDays` is dead

**File:** `src/Csps.Domain/Analytics/AnalyticsRetention.cs:9-13,15-16`; `src/Csps.Infrastructure/Analytics/AnalyticsRetentionJob.cs:156-159`

**Issue:**
- The consent constant cites D-04 and the daily years constant cites D-05. The 12.1 context and the retention job cite them the other way round: D-04 is the 3-year daily keep, D-05 is the consent record keep.
- `AnalyticsRetention.SaltDays` (2) is used nowhere in `src`. `PurgeSaltsAsync` hard-codes "older than yesterday". Only a test pins the constant, so it can drift from the real behavior.

**Fix:** Swap the decision ids in the two summaries. Make `PurgeSaltsAsync` use `today.AddDays(-(SaltDays - 1))`, or delete the constant and its test.

### IN-G1-06: CSV export fails with a generic 500 if a stored page key does not start with a letter

**File:** `src/Csps.Application/Analytics/VisitorStatsCsv.cs:46-51`; `src/Csps.Application/Analytics/PageNames.cs:39`

**Issue:**
- `NameFor` returns an unknown stored key as is, and `SafePage` throws `ArgumentException` for any key that does not start with a letter or holds a comma, quote or line break.
- Today only the resolver writes keys, so this cannot happen.
- The Manager would still get "Something went wrong" for the whole export, not one odd row, if a future key (or a hand-edited row) broke the rule. The unused-table drop and the retired `cookies` key make this a plausible future edge.

**Fix:** Keep the formula guard but degrade instead of throwing. For example, prefix an unsafe name with `'`, or fall back to a fixed `Other` for a name that fails the check. Keep the throw only in `Write` for programmer misuse, and have the handler sanitize first.

### IN-G1-07: The Testing seed returns 500, not 400, for a very large negative offset

**File:** `src/Csps.Server/Controllers/TestingAnalyticsController.cs:101-103`

**Issue:**
- `today.AddDays(offset)` throws `ArgumentOutOfRangeException` for an offset such as `int.MinValue` before the floor check.
- The `Invalid` 400 path is skipped.
- Testing-only and compiled out of Release, so low risk.

**Fix:** Bound the offset first, for example `OffsetDays: <= 0 and >= -1100` (3 years plus slack), then compute the date.

# Phase 12.1 G2: Code Review Report (web app)
*Created: 2026-11-19T07:00:00-06:00 · Updated: 2026-11-19T07:00:00-06:00*

**Depth:** standard. **Scope:** the 27 listed files, read in full, with `git diff f579e158` for what this phase changed.

## Summary

The web side of the phase is sound. I found no crash, no security hole and no break of D-53, D-54, D-59 or D-65.

What I checked and found correct:

- **Map tap storage (`mapChoice.ts`, `MapCard.tsx`):**
  - Every storage access sits inside try and catch, including the read of `window.localStorage` itself.
  - Only the exact value `show` reads as true.
  - It is browser storage, not a cookie.
  - `useSyncExternalStore` returns a stable boolean and has a server snapshot.
  - Focus moves into the frame only after the visitor's own tap.
  - The frame source is limited to the CSP-allowed embed prefix.
- **Page-view beacon:** sends the path only, with no query or fragment. It skips `/admin` and `/dev`, and a failed send is dropped. A same-path repeat is de-duplicated. The service is loaded on demand.
- **Removed code:** no leftover import, route, link, copy key or storage use of the consent code, the Cookie Policy, web-vitals, the speed report or the `circle-x` icon remains in non-test `web/src`.
- **OR-4:** none of the 27 files contains an en or em dash.
- **Visitor Stats service:**
  - It checks the CSV header `Date,Page,Page views` (D-69) and the server's own file name pattern.
  - It refuses a count that is not a plain number.
  - The shapes match the generated API type: no unique visitors, and top pages are page keys the client maps to names.
  - The 3-year date floor (D-70) is in `visitorStatsRange.ts`.
- **Cookie facts in `legalPrivacy.ts`:** the cookie names (`__Secure-csps_rt`, `_2fa`, `_staff`) and the staff marker lifetime match `AuthCookies.cs` and `AnalyticsCookies.cs`. The two retired cookies are cleared by `RetiredCookiesMiddleware`.
- **D-73:** the Privacy Policy keeps `approved: false` (the DRAFT notice shows). Its version and date match `tests/fixtures/legal-pages.json`.

The one real defect is legal text that stops being true once the saved map setting exists.

## Warnings

### WR-G2-01: Privacy Policy says Google loads "only after you tap Show Map", but the saved setting loads it with no tap

**File:** `web/src/modules/public/legalPrivacy.ts:78` and `web/src/modules/public/legalPrivacy.ts:114`
**Issue:** Two lines still carry the pre-D-65 promise:

- Line 78 (term "The map"): "The map loads from Google only after you tap Show Map."
- Line 114 (list "Who else handles it"): "Google, for the map on the Contact page. This happens only when you tap Show Map."

Under D-65 the tap is saved in the browser. On every later visit from that browser, `MapCard` renders the Google frame on first render with no tap. For a returning visitor, Google is contacted on page open, so the statements are false. The page does explain the saved setting in "Cookies and saved settings" (lines 208-218), so the policy contradicts itself. The owner's rule says legal text must not promise what the site does not do, and the owner is about to approve this wording (D-73). D-66 keeps the map box wording ("The map loads from Google when you tap Show Map") unchanged. That line is shown only while the map is offered, so it stays true. The policy lines are different, because they describe the site as a whole.

**Fix:** Reword both lines so they say "the first time" and point to the saved setting:
```ts
// line 78
'To show the Google map on the Contact page. The map loads from Google when you tap Show Map. After your first tap, this browser loads the map by itself until you clear the saved map setting (see "Cookies and saved settings"). Our basis is your consent: that tap is your choice.',
// line 114
['Google, for the map on the Contact page. This happens after you tap Show Map, and on later visits from the same browser until you clear the saved map setting.'],
```
Update `PrivacyPolicyPage.test.tsx` if it asserts the old wording. Since it is owner-approved text, the owner has the final word on the wording.

## Info

### IN-G2-01: A single KPI card sits in a three-column grid

**File:** `web/src/modules/admin/components/visitorStats.recipe.ts:24-26`
**Issue:** `visitorKpiRowClasses` still declares `grid-cols-[repeat(3,minmax(0,1fr))]`, but `VisitorKpiRow` now renders one card. At 1024 px and wider, the Page views card fills only the left third of the row and leaves two empty columns. The doc comment above it was changed to say "two columns up to 1023px", which describes a layout that is now meaningless for one card. This is a visual matter, so it is the owner's call.
**Fix:** If a full-width card is wanted, use a single column (`grid-cols-[minmax(0,1fr)]`) and drop the `pg-tablet:grid-cols-2` override. If the third-width card is intended, keep the code and correct the comment.

### IN-G2-02: "These two settings" in the Privacy Policy covers three stored keys

**File:** `web/src/modules/public/legalPrivacy.ts:196` (with the entry at 202-207)
**Issue:** The text reads "These two settings are not cookies." The list has two entries, but "Admin settings in this browser" bundles two keys: `csps-theme` and `csps-orders-view`. The map setting is the third, so the browser holds three stored values. The entry does say "the admin theme and the orders view", so it is not wrong, only imprecise.
**Fix:** Write "These settings are not cookies." and drop the count, so a later admin setting does not make it stale.

### IN-G2-03: `showContactBar` is now a pure alias of `onContact`

**File:** `web/src/layouts/PublicLayout.tsx:57`
**Issue:** After D-30 was removed, `const showContactBar = onContact;` adds a name with no meaning. It is used at the scroll-padding line and in the Contact bar render.
**Fix:** Use `onContact` directly and delete the alias.

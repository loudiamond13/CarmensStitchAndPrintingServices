# Phase 12.1: Analytics simplification: daily page tally only, no cookie banner - Research
*Created: 2026-11-18T19:10:00-06:00 · Updated: 2026-11-18T19:10:00-06:00*

**Researched:** 2026-11-18
**Domain:** Removing a consent and analytics feature from a .NET 10 + React 19 app, plus small additive pieces (site-wide rate ceiling, old-cookie expiry, a saved map setting, a smaller stats page, a folded legal page)
**Confidence:** HIGH for the inventory and the code facts (read this session); MEDIUM for the proposed shapes (they are design choices); LOW items are listed in the Assumptions Log.

## Summary

Phase 12.1 is mostly a removal. Phase 12 built a full consent stack: a cookie bar, a Cookie Settings window, three anonymous write routes besides the page view (`/consent`, `/clear`, `/vitals`), a visitor id cookie, visit and speed sample tables, a monthly roll-up, a web-vitals loader, and a stats page with unique visitors, visits, sources, devices and page speed. D-53, D-54 and D-59 cut all of that down to one anonymous counter (`DailyPageCounts`), one route (`POST /api/v1/analytics/page-views`) and a three-part stats page. The tables stay (D-56, D-61, D-64), so **no migration is written** and the EF model must stay byte-for-byte the same (`MigrationScriptTests` checks `HasPendingModelChanges()`).

Four pieces are new, and each needs a failing test first: (1) the D-51 site-wide ceiling on the page view route, which was ruled but **never built** (only per-address limits exist today); (2) the D-63 expiry of `__Host-csps_consent` and `__Secure-csps_vid`, best done in a tiny middleware with exact matching cookie attributes; (3) the D-65 saved map setting in local storage, read synchronously so the frame shows on first render; (4) the reshaped stats answer and the `Date,Page,Page views` CSV. The legal work folds the Cookie Policy into the Privacy Policy, removes `/cookies` from about 25 places, and puts the Privacy Policy back to DRAFT until the owner checkpoint (D-71, D-73).

The biggest planning risk is **ordering across shared files**: the generated OpenAPI types, the cookie inventory test (which reads cookie names out of `AnalyticsCookies.cs`), the global web test setup (which seeds a consent cookie into every test), and the e2e fixture (which plants a consent cookie into every browser). A wrong order breaks the build between commits. The recommended order is web consent removal first, then server removal, then legal and stats, then the owner checkpoint.

**Primary recommendation:** Remove the client consent stack first (web never calls the removed routes again), then remove the server routes and regenerate the API types in one plan, then do the legal fold and the stats reshape as vertical slices, and keep every new behavior (ceiling, cookie expiry, map setting, CSV, stats shape) test-first.

### Locked Decisions
All rulings below: owner, 2026-11-18, in this discussion. Numbering continues from Phase 12 (D-01 to D-58 are in `.planning/phases/12-consent-analytics-legal/12-CONTEXT.md`).

#### Leftover cookie code
- **D-59:** **Remove all the old consent code.** The cookie bar, the Cookie Settings window, the footer "Cookie settings" button, the consent route (`POST /api/v1/analytics/consent`), the clear route (`POST /api/v1/analytics/clear`), the speed sample route (`POST /api/v1/analytics/vitals`), their handlers, validators, ports and tests, the client consent modules (`consentCookie`, `consentJar`, `consentPolicy`, `consentRules`, `consentFocus`, `consentCopy`) and the dev previews and scenarios for them. The `web-vitals` package (D-38) is uninstalled. Only the page view route stays, and it only increments `DailyPageCounts`. The database tables stay (D-56). — **Reversibility:** costly — bringing stats back means rebuilding the consent flow, routes and tests.
- **D-60:** **Keep `/.well-known/gpc.json`** (D-39). It stays true: the site tracks no one, so it honors the signal by default.
- **D-61:** **The consent record table stays, unused, like D-56.** Nothing new is written. The monthly cleanup keeps removing old rows. Dropping it joins the D-56 drop list and needs a separate owner yes.
- **D-62:** **Phase 12 and Phase 12.1 go live together.** Phase 12 is never deployed alone, so no real visitor ever sees the cookie bar.
- **D-63:** **The server expires the old consent cookie and the old visitor id cookie when a browser still sends them** (browsers used in testing). Then the site can truthfully say it sets no optional cookies.
- **D-64:** **The monthly roll-up into the daily device and source totals stops.** Those two tables (`DailyDeviceCount`, `DailyReferrerCount`) stay, unused, and join the D-56 drop list. The monthly cleanup still ages out old rows in every analytics table.

#### Map tap
- **D-65:** **The Show Map tap is saved in the browser's local storage (amends D-55).** After one tap, the map loads by itself on every later visit from that browser. There is still no cookie banner: the tap itself is the choice.
  - The saved setting has no expiry. It lasts until the visitor clears their browser data.
  - There is no on-page button to undo it. The Privacy Policy explains how to clear it in the browser.
  - It is saved for browsers that send GPC too: the tap is a clear choice by the visitor (same reasoning as D-20).
  - One setting covers every Google map on the site, now and later.
  - The Privacy Policy lists this one saved setting (D-72).
- **D-66:** **Map wording and Directions stay as they are.** The box keeps "The map loads from Google when you tap Show Map." with no extra line about Google cookies. The Directions link stays a plain link that needs no tap first.

#### Visitor Stats details
- **D-67:** **The most viewed pages list shows the top 5**, each with its count and share of all views. The full detail is in the CSV.
- **D-68:** **The chart keeps choosing per day or per month by itself** (per day up to 62 days, per month for longer ranges, `StatsBucket`). No Day / Month switch.
- **D-69:** **The CSV export is one row per day per page:** `Date,Page,Page views`. Days with no views for a page are left out. This replaces the D-25 / D-33 export shape. The file name keeps the `visitor-stats-{from}-to-{to}.csv` pattern.
- **D-70:** **The date picker reaches back 3 years**, matching what is kept (D-04). The 13-month note, the "Not available" markers and the unique visitors and visits figures are removed (D-27 no longer applies).

#### Policy wording and version
- **D-71:** **The Privacy Policy stays version 1.0, rewritten in place, with the DRAFT notice back on until the owner re-approves it.** No visitor ever saw the first 1.0, because the site is not live (D-62).
- **D-72:** **The Cookie Policy is folded into the Privacy Policy (amends D-58).** The Privacy Policy gets a section on cookies and saved settings: the necessary cookies, the saved map setting (D-65), that Google may set its own cookies when the map loads, and how to clear them. The `/cookies` page is removed and shows the normal "page not found" (no redirect). The footer Legal row has three links: Privacy Policy, Terms of Use, Accessibility Statement. Links to the Cookie Policy from other pages move to the Privacy Policy. — **Reversibility:** reversible — a new page and footer link can be added back in a later release.
- **D-73:** **Review flow: Claude drafts the new Privacy Policy wording in plain words, then a plan stops at a checkpoint for the owner's yes**, like Phase 12's plan 12-22. If the owner is away, the checkpoint is parked in the backlog and the page keeps its DRAFT notice.

## D-63: Expiring the Old Cookies

**The cookies** [VERIFIED: `src/Csps.Server/Security/AnalyticsCookies.cs:10-19, 36-44, 95-102`]:

| Cookie | Name constant | Attributes it was set with |
|--------|---------------|----------------------------|
| Consent | `ConsentCookieName = "__Host-csps_consent"` | `HttpOnly = false, Secure = true, SameSite = SameSiteMode.Lax, Path = "/"`, no Domain |
| Visitor id | `VisitorCookieName = "__Secure-csps_vid"` | `HttpOnly = true, Secure = true, SameSite = SameSiteMode.Strict, Path = CookiePath` where `CookiePath = "/api/v1/analytics"`, no Domain |

**Why the attributes matter.** A browser replaces a stored cookie only when the new Set-Cookie has the same name, domain and path, then evicts it once expired [CITED: rfc-editor.org/rfc/rfc6265#section-5.3 step 11 and the eviction rule]. A `__Host-` cookie must carry `Secure`, `Path=/` and no `Domain`, or the browser rejects the Set-Cookie, including a deleting one [CITED: developer.mozilla.org Set-Cookie, "Cookie prefixes"]. `__Secure-` needs `Secure`. So the delete must use exactly `Path=/` + `Secure` for the consent cookie and `Path=/api/v1/analytics` + `Secure` for the visitor id. Mirror `HttpOnly` and `SameSite` too (harmless, and `ExpireVisitor` already does this at `AnalyticsCookies.cs:63-67`).

**Where the browser sends them.** The consent cookie (Path=/) comes with every request to the origin: the shell document, the API and static files. The visitor id (Path=/api/v1/analytics, SameSite Strict) comes only with `POST /api/v1/analytics/page-views`, which `PublicLayout` sends on every public route change.

**Recommended: a small middleware** (for example `src/Csps.Server/Http/RetiredCookiesMiddleware.cs`), registered right after `app.UseStaticFiles(...)` (Program.cs line 131) and before `app.UseRouting()` (line 134):
- When `Request.Cookies` contains either retired name, register `Response.OnStarting` that calls `Response.Cookies.Delete(name, options)` with the matching options above. `OnStarting` is the pattern `SecurityHeadersMiddleware` uses so headers survive the exception handler's response clear [VERIFIED: `SecurityHeadersMiddleware.cs` summary and `InvokeAsync`].
- Placing it after the static file middleware means hashed assets (long cache) never carry a Set-Cookie; the shell, `/sitemap.xml`, `/robots.txt`, `gpc.json` and every API answer do.
- It never touches `__Secure-csps_rt`, `__Secure-csps_2fa` or `__Secure-csps_staff`.
- Alternative considered: delete only inside the page view action. Simpler, but misses admin-only browsers (no beacon there) and any answer the limiter or the CSRF filter ends first (429/403). The middleware covers both for one dictionary lookup per request.

**Where the two names live.** `web/src/test/cookie-inventory.node.test.ts` reads every quoted `__Host-`/`__Secure-csps_*` string out of `CODE_FILES = ['AuthCookies.cs', 'AnalyticsCookies.cs']` and requires each to be a term in the policy [VERIFIED: `cookie-inventory.node.test.ts:12-15, 93-110`]. If the retired names stay in `AnalyticsCookies.cs`, the Privacy Policy would have to list cookies the site no longer sets. So, **in the legal plan**, move them to a new file outside `CODE_FILES` (for example `src/Csps.Server/Security/RetiredCookies.cs`), retarget the inventory test from `COOKIES_TEXT` to `PRIVACY_TEXT`, and add one assertion that no retired name appears in the policy. Until the legal plan lands, the server plan can keep the constants in `AnalyticsCookies.cs` so the old inventory test still passes against the old Cookie Policy text (see § Plan Ordering).

**Tests (red first):** integration tests with `HandleCookies = false` and a hand-written `Cookie` header:
- `GET /` with `__Host-csps_consent=x` gets `Set-Cookie: __Host-csps_consent=; expires=Thu, 01 Jan 1970 ...; path=/; secure; samesite=lax`, with no `domain=`.
- `POST /api/v1/analytics/page-views` with `__Secure-csps_vid=x` gets the delete with `path=/api/v1/analytics; secure; samesite=strict; httponly`.
- No retired cookie sent: no such Set-Cookie. A static asset request: no Set-Cookie. A request carrying `__Secure-csps_rt` or `__Secure-csps_staff` never gets those deleted.
- Reuse `SetCookieOf`, `ValueOf`, `ExpiresOf` (moved helpers) and the `AssertExpired` pattern (ConsentEndpointTests.cs:393-403).
- E2E (replaces `gpc.spec.ts`): `context.addCookies` with `__Host-csps_consent` (`url: origin`) and `__Secure-csps_vid` (`domain`, `path: '/api/v1/analytics'`, `secure`, `httpOnly`, `sameSite: 'Strict'`); open Home and wait for the page view request; `context.cookies()` holds neither.

## Common Pitfalls

### Pitfall 1: The raw purge stops for good
**What goes wrong:** old visit, page view and speed rows are never deleted. **Why:** `PurgeRawVisitsAsync` purges only through the roll-up cursor (`AnalyticsRetentionJob.cs:171-178`), and D-64 stops the roll-up. **How to avoid:** purge by `RawCut(today)` directly; add a red test with rows older than the cut and no cursor row. **Warning sign:** "Old visit records removed" stays 0 on a database with old rows.

### Pitfall 2: The e2e fixture fights D-63
**What goes wrong:** every e2e browser gets `__Host-csps_consent` from `addDecidedConsent`, and the server deletes it on every answer; tests that count cookies or Set-Cookie headers fail. **How to avoid:** remove the fixture's consent option in plan A, before the middleware lands in plan C.

### Pitfall 3: Test helpers vanish with ConsentEndpointTests
**What goes wrong:** `AnalyticsRateLimitTests` stops compiling. **How to avoid:** move `NewClient`, `NewPost`, `SetCookieOf`, `ValueOf`, `ExpiresOf` to a helper file first.

### Pitfall 4: Generated types break the web typecheck
**What goes wrong:** regenerating the OpenAPI types drops `ConsentDecisionResponse`, `VitalsRequest` and old stats types while web files still import them. **How to avoid:** web removal first (plan A); the stats reshape regenerates and updates the web service in the same plan (F); never run two regenerating plans in parallel worktrees.

### Pitfall 5: The cookie inventory test points at the wrong file or text
**What goes wrong:** moving the cookie names out of `AnalyticsCookies.cs` while the Cookie Policy still lists them fails "is in the policy but not set by the code"; keeping them there after the fold fails "is set by the code but not in the policy". **How to avoid:** move the names and retarget the test in the legal plan, in one commit.

### Pitfall 6: Deleting a cookie with the wrong attributes does nothing
**What goes wrong:** a delete without `Path=/api/v1/analytics` leaves the visitor id in place; a `__Host-` delete without `Secure` and `Path=/` is rejected. **How to avoid:** reuse the exact options the cookies were set with (§ D-63) and assert the attributes in the tests. **Warning sign:** e2e `context.cookies()` still lists the cookie after a page view.

### Pitfall 7: The map flashes the drawing for a returning visitor
**What goes wrong:** reading storage in `useEffect` paints the drawing first, then the frame (layout is stable, but it looks broken and costs a second render). **How to avoid:** `useSyncExternalStore` (or a lazy `useState` initializer) reads storage during the first render.

### Pitfall 8: Privacy DRAFT breaks sitemap and approval tests
**What goes wrong:** `/privacy` leaves the sitemap and gets `noindex` again; `LegalPagesTests.EveryPageIsApprovedAtVersionOnePointZeroOnTheOwnersDate`, `LegalPages.test.tsx:36` and `link-preview.spec.ts:182` fail. **How to avoid:** update these tests to read the shared fixture, then the checkpoint flips the flag back.

### Pitfall 9: The schema drifts
**What goes wrong:** removing `ReferrerName` entirely or an enum that an entity uses changes the model, and `HasPendingModelChanges()` fails (or someone runs `migrations add` and creates a drop). **How to avoid:** keep entities, enums and `MaxLength` constants; never run `dotnet ef migrations add` in this phase.

### Pitfall 10: The ceiling throttles the test suites
**What goes wrong:** many test classes post page views through `CspsApiFactory`, and five Playwright projects share one address; a 600-a-minute ceiling makes them flaky. **How to avoid:** set the ceiling high in `CspsApiFactory`, Playwright and `owner-review.mjs`; real 600 only in `RealLimitsFactory`.

### Pitfall 11: Coverage dips under 90%
**What goes wrong:** branches were 90.32%; removing well-covered files changes the ratio. **How to avoid:** measure after plan A and plan F; add focused tests if needed.

```ts
export const MAPS_KEY = 'csps-maps';
const SHOWN = 'show';
const listeners = new Set<() => void>();

export function readMapsShown(): boolean {
  try {
    return window.localStorage.getItem(MAPS_KEY) === SHOWN;
  } catch {
    return false;
  }
}

export function saveMapsShown(): void {
  try {
    window.localStorage.setItem(MAPS_KEY, SHOWN);
  } catch {
    // Blocked storage: the map still shows for this view.
  }
  for (const listener of listeners) listener();
}

export function subscribeMapsShown(onChange: () => void): () => void {
  listeners.add(onChange);
  window.addEventListener('storage', onChange);
  return () => {
    listeners.delete(onChange);
    window.removeEventListener('storage', onChange);
  };
}
```

### Known Threat Patterns
| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Beacon flooding to inflate counts or load the database | Denial of service / Tampering | Per-address limit + site-wide ceiling; the counter table grows at most one row per page per day; documented as inflatable (anonymous). |
| CSV formula injection (CWE-1236) through the new page cell | Tampering | Only fixed page names or keys reach the cell; a test asserts no cell starts with `= + - @`, tab or CR. |
| Crafted old cookies to reach removed logic | Spoofing | The code that read them is gone; the middleware only deletes. |
| Tampered `csps-maps` value | Tampering | Only the exact value `'show'` counts; the effect is limited to the visitor's own browser loading the Google frame the CSP already allows. |
| Path with query or fragment storing search text (WEB-10 privacy) | Information disclosure | Client sends `location.pathname`; server cuts at `?` and `#` before the page key lookup. |
| Draft legal text indexed | Information disclosure (minor) | `noindex` and sitemap exclusion while `approved: false`. |

# Plan 09-32: The monthly run backs up the database first and keeps its own newest 3 backups

*Created: 2026-10-31T18:55:00-05:00 · Updated: 2026-10-31T19:15:00-05:00*

> MVP note: the ROADMAP Goal line for Phase 9 is not in user-story form. No story was invented.

<objective>
The second half of the monthly database backup (D-39, split by D-48): one more maintenance job writes a `.bak` of the live database into the host's `db` folder once a month through plan 09-31's statement, keeps its own newest 3 files (D-41), never writes twice inside 20 days (D-46), tries at most once a day, and turns the run red when a backup fails, cannot clean up or is not set up (D-43, D-47).

Purpose: this delivers CUT-01's "scheduled DB backups enabled" item early. CUT-01's other items (least-privilege login, a restore tested once, TLS and HSTS, SPF/DKIM/DMARC) stay with Phase 17. JOB-01: the backup is one more short, leased job behind the key-protected endpoint, and nothing relies on in-memory state: the 20-day guard reads the files, the one-try-a-day guard reads a DatabaseLocks claim.
Output: the store and attempt-lock ports and adapters, the settings, the file-name rules, the job and its registration, tests, the backup section of the runbook and the run-summary row in the UI-SPEC.

Wave note: wave 8, after 09-28, because this plan edits `docs/operations/maintenance.md` (09-12, 09-17, 09-22, 09-28) and both maintenance registrations (09-25, 09-28). 09-22 matters too: its script repeats calls while `more` is true (at most 10) and reads any answer with ok false as a red run, which is why the job has both guards and why the skipped line on a repeat call can stay plain.

Phase goal (ROADMAP, verbatim): "Staff can attach, arrange and view order photos, including straight from a phone camera. The photos load fast and stay private per the OD-9 ruling. Storage cleanup and token purges run as short, reliable, scheduled jobs."
</objective>

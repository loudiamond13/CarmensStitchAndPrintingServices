# Plan 09-01: Upload one photo to an order through the API

*Created: 2026-10-31T18:00:00-05:00 · Updated: 2026-10-31T11:52:00-05:00*

<objective>
Size note: this plan touches 36 files, above the checker's soft limit, under the owner's D-38 exception (owner, 2026-10-31). Do not split it.

The phase tracer on the server. Staff (or any API client, such as the future Android app) send one JPEG for an order; the server checks the order, sniffs the bytes in memory, hands them to the image storage port, saves the photo row under the order's row lock, audits it and answers the whole order. Tests use the in-memory `TestingImageStorage` (D-07); outside Testing the storage answers 503 until plan 09-19 adds Cloudinary.

Purpose: proves every server layer for photos end to end (Domain child, EF table with the 5-photo guard, port, handler, controller, error mapping) before any expansion (D-01, D-08, D-11, D-12, D-19; ORD-04, IMG-01, IMG-02, IMG-03).
Output: `OrderImage`, `OrderImageRules`, `Order.AddImage`, the `AddOrderImages` migration, `IImageStorage`, JPEG sniffing, `ErrorKind.Unavailable`, `UploadOrderImageHandler`, `OrderImagesController`, the matrix row, the OpenAPI snapshot and generated web types.

Split note (revision 2026-10-31, plan budget): the endpoint proof of the limits, the size rules and the no-disk rule is plan 09-05; the image rules endpoint, the Testing image routes and the upload docs are plan 09-09; the photo list in the order answer is plan 09-07.

Phase goal (ROADMAP, verbatim): "Staff can attach, arrange and view order photos, including straight from a phone camera. The photos load fast and stay private per the OD-9 ruling. Storage cleanup and token purges run as short, reliable, scheduled jobs."

Serial contract rule: the plans that rewrite `tools/openapi-gen/openapi.v1.json` and `web/src/types/api.generated.ts` are 09-01, 09-07, 09-09, 09-13, 09-20 and 09-26, each in its own wave.

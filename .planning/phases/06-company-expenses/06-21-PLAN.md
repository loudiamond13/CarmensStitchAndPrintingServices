## What each lock guarantees today (read from the code and its tests)

| File | Lock today | Guarantee | Proven by |
|------|------------|-----------|-----------|
| `ManagerRosterLock.cs` | one exclusive, transaction-owned SQL Server application lock on a fixed name, 10-second wait | the Manager-count check and the change commit before another roster change reads the count, so at least one active Manager always remains | `LastManagerGuardTests` (four 10 or 20-round races over HTTP) |
| `AccountTokenStore.LockAccountAsync` | the same, on a name per person, 10-second wait | a second link request for the same person waits for the first to commit, sees its link and revokes it: one usable link per person per purpose | `ForgotPasswordTests.TwoRequestsAtTheSameMomentLeaveExactlyOneUsableToken` (one round) |
| `IdempotencyGate` | the same, on a hash of key, route and user, **no wait** | a duplicate that arrives while the first runs is turned away at once (409 in-progress); the stored answer commits with the business change; a rollback frees the key | `IdempotencyTests.ADuplicateThatArrivesWhileTheFirstRunsGetsAConflict` (one round) and the store, keep, throw and expiry cases |

Design chosen (Claude's discretion inside D-50, all EF-only):
- **Roster and account locks: standing lock rows.** A row is locked by an `ExecuteUpdateAsync` inside the caller's transaction and held to commit, exactly like the old transaction-owned lock. The per-person lock uses 64 fixed rows chosen from the person's id (lock striping) instead of one row per person, because EF has no insert-without-SaveChanges and a row created on demand would need a second connection whose wait SQL Server cannot see in a deadlock. Two people on the same row only take turns.
- **Duplicate request guard: a committed claim row with a short lease.** The old lock answered "busy" without waiting. EF cannot ask SQL Server not to wait, so a row locked inside the transaction would make the duplicate wait and then replay, which changes the API. A claim row committed on its own makes the duplicate fail at once on the primary key, so it still gets 409 in-progress. The cost is a lease: after a crash the key stays "in progress" until the lease ends. The stored-record unique index keeps exactly-once even then.
- No step plans hand-written SQL. If any part cannot be built this way, stop and report; do not work around it with raw SQL.

The tab head already has the primary Add Discount, and a second button with the same name would be harder to use with a screen reader and in tests. Same call as 08-16 item 1. Say if the owner wants the ghost button as well.
2. **SPEC-GAP, owner review: a percent Value accepts only digits and one point, with at most 3 digits before the point.** The spec says `Field prefix="%"` with `inputMode="decimal"` and gives no typing rule. A key that is not a digit or a point is ignored, as the money box does. A third decimal place can still be typed, so the server's "Use at most 2 decimal places." shows. Text that is not a number cannot reach the check, but if it did it reads with the percentage words. Words: `orderDiscountCopy.ts`, `errors.percentOutOfRange`. The rule lives in `OrderDiscountModal.tsx` (`PERCENT_TEXT`).
3. **The Computed amount is shown as ₱0.00 while Value is empty or not a number.** The spec gives the line but not its empty state. It is a labelled preview: the saved figure is always the server's.
4. **The items-total cap adds each other discount rounded to the centavo, then compares with the items total.** This follows the pinned operation order in `csps.ts` (round each discount, sum, subtract). The server decides; a 422 `orders.discount-above-subtotal` shows its sentence in the window banner and keeps what was typed.
5. **An edit's cap leaves out the discount's own saved amount** (`otherDiscountsTotal(order, discountId)`). After Load Latest the cap follows the latest discounts.
6. **Switching Type clears Value in edit mode too.** The spec says so for the window; the form then counts as changed, so Cancel asks "Discard changes?".
7. **A server 400 on `kind` has no field to sit under.** Type is a radio group, so a message for `kind` is shown in the window banner. The browser always sends one of the two kinds, so this cannot happen from the screen.
8. **Add Discount stays on an order that already has 20 discounts.** The server refuses the 21st with `422 orders.too-many-discounts`; the window shows that sentence in its banner. The browser does not count them (the spec names no browser check).
9. **`OrderTabs.test.tsx` was edited (outside this plan's file list).** Its Discounts table tests rendered the tab on an active order with no providers. The tab now needs the query client and toasts when its actions show, so those tests pass `readOnly` (the table content they check is the same). The editable tab is covered by `OrderDiscountsTab.test.tsx`. Same fix as 08-16 item 10.
10. **The footer total no longer spans the actions column.** The footer label spans the data columns only (`columns` without the actions column), so the Total discount figure stays under Amount. Found by the add test going red when the actions column arrived.
11. **After a save or delete, focus goes to the same place as the other tabs.** Add returns to Add Discount, Edit to that row's Edit button, Delete to the next row's Edit (else the previous, else the tab heading). The tab names the target itself because WebKit does not focus a button on click (08-14).
12. **TDD record.** Round 1 RED: service, schema and add-window tests failed on module-not-found (the files did not exist). Round 1 GREEN: all 61 passed first run; lint then found one `no-unnecessary-condition` error in the schema (a string compared twice), fixed with a `kindOf` helper. The tab Add tests and the locked and read-only tests were written in the same GREEN commit, and the locked and read-only ones were green at once (the tab showed nothing for them before). The credit-toast tests were already green at RED because the toast text comes from the shared `orderSavedMessage` built in 08-14; they stay as regression tests.

## From plan 08-19

1. **SPEC-GAP, owner review: where the Change Status popover opens.** The UI-SPEC gives the menu's items but not where the popover hangs. It opens under the button at the button's left edge; on a phone it hangs from the button's right edge and is never wider than the screen, so the page does not scroll sideways (the `@orders-status` e2e checks that with the menu open in all five projects). Classes: `orderStatusMenuPopoverClasses` in `orderPage.recipe.ts`.
2. **SPEC-GAP, owner review: every failed move has one toast title, "Couldn't change the status".** The UI-SPEC names that title for a status failure and says the message is "the server line or the P2 mapper line". A 422 shows the server's sentence. A 404 shows "This order was not found or was deleted." (the same sentence as the page). Every other failure shows the usual P2 line (for example "You don't have access to this. Ask a Manager if you need it."). Server text of any other status is never shown. Words: `ORDER_PAGE_COPY.status`.
3. **The Refunds tab keeps its tab but this plan builds no refund control.** The page still shows the Refunds tab on a Cancelled order (`showRefundsTab`). The "Record Refund" button and the refund windows come from the refunds plan. This plan adds no refund path: the cancel sends only the status, and a test checks no write goes to a refund route (D-18, 07 D-07).
4. **The cancel message names the server's paid figure.** "Payments of ₱X" uses `totals.paid`, which is the money collected before any refund. An order that already has refunds still says it. The two sentences are joined into one paragraph (money line, then "You can reopen it later.").
5. **A refusal while cancelling shows inside the Cancel dialog** (the server sentence, or "This order was not found or was deleted."), and the dialog stays open. A refusal on a move, on Mark Completed or on Reopen Order from the menu shows the danger toast; in the Reopen window it shows as a line under the choices. The order is read again after a 422 or a 404 in all of them, so the next menu open reflects the latest order (UIC-24).
6. **Focus after a change is carried out by the page, by element id.** The Change Status button has the id `order-change-status` and the banner's Reopen Order has `order-reopen` (`orderStatus.ts`). `OrderBody` keeps a focus wish ("reopen" after a complete or cancel, "status" after a reopen) and carries it out after the render that shows the button. A dismissed Reopen window sets the wish back to Reopen Order, because WebKit does not focus a button on click and the window has nothing to return to (the same reason as 08-14).
7. **The Cancel dialog lives inside the menu component and goes with it.** When the cancel succeeds the order locks, the menu leaves the page, and the dialog with it, so its exit animation does not play. The toast, the banner and the focus on Reopen Order follow at once. Keep Order keeps the menu and returns focus to Change Status (tested).
8. **The Reopen window puts the focus on the checked radio.** The Modal takes a ref for the first focus; `ReopenOrderModal` passes a small object whose `current` finds the checked radio when the window opens, so the arrow keys start from the choice. A radio group's first radio would otherwise take it.
9. **A move sent twice in a row from a failed network keeps one key per status.** The menu keys a submission by "order id + status" (the `useOrderAction` target id), so a retry of the same move keeps its Idempotency-Key and a different status is a new submission with a new key.
10. **Extra files outside the plan list:** `OrderStatusDot.tsx` (the 7px dot used by the menu and the Reopen window), `orderStatus.ts` (status label, the other active statuses, the two element ids) and the new classes in `orderPage.recipe.ts`. `OrderHeader.tsx` got an `onStatusMoved` prop so the page can set its focus wish.
11. **For plan 08-21: the deleted view must not show the Change Status menu or the locked banner.** `OrderHeader` draws the menu for any order that `canEditOrder` allows, and `OrderBody` draws the banner for a Completed or Cancelled order. A deleted order that is still Pending to Delivered would get the menu if the deleted view reused `OrderHeader` as it is; that view builds its own header and body (UI-SPEC X2), so it should not, and should check this.

Task 2 RED: 15 failed on the planned assertions (no dialog, no banner, no toast). GREEN: all 103 passed first run.

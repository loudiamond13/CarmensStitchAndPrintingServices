# Plan 11-39: Redraw every photo before upload, so its location never leaves the phone (UAT G-11-19)

*Created: 2026-11-14T19:25:00-06:00 · Updated: 2026-11-14T19:25:00-06:00*

<objective>
Close UAT gap G-11-19 (test 19, minor) under ruling D-P11-BL-65 (owner, 2026-11-14). Today prepareImage in web/src/utils/images.ts redraws a photo only when it must be shrunk. A photo already 2000 px or smaller goes up as the picked file, with its location and camera data. The server strips that data before storing, so nothing was ever saved or published with it, but it still left the phone.

The fix: every photo the browser can decode goes through the same canvas redraw the shrink path uses, at its own size when no shrink is needed. The one exception stays: a HEIC the browser cannot decode is sent as it is, and the server strips it. prepareImage is shared by order photos (Phase 9), product line photos, gallery uploads and the share picture, so all four get the fix with no caller change. This amends Phase 9 D-18 ("a file already within that size is left as it is"); 09-CONTEXT.md already carries the amendment.

Purpose: the privacy rule that every upload is redrawn (rules 11-22 D8 and 11-34 D9, UAT test 19) becomes true in code.
Output: the prepareImage change with its pinned tests, cleaned comments, the 09-UI-SPEC step 3 amendment, and the UAT fix_plan record.
</objective>

<interfaces>
- prepareImage(file, rules, parts) today: sniffImageType on the first 32 bytes ('type' when null); parts.decode; on a decode error a non-HEIC is 'unreadable' and a HEIC is returned as the picked File (type 'image/heic', width and height null, preview null, previewUnavailable true) or 'size' when file.size is over rules.maxBytes. After decoding: 0-size is 'unreadable'; width times height over MAX_ORIGINAL_PIXELS (100 MP) is 'pixels'; planDownscale(width, height) gives the prepared size; that size over rules.maxPixels or rules.maxSide is 'pixels' with no encode; previewOf makes the 176 px preview. Then the branch to remove: when `plan.scaled` is false it checks file.size against maxBytes and returns the picked File with MIME_OF_KIND[kind]. Otherwise encodeSameFamily(parts, bitmap, plan, kind) runs: null is 'unreadable', blob.size over maxBytes is 'size', and it returns the blob with withExtension(file.name, extension), blob.type and the plan's size. A catch gives 'unreadable' and finally closes the bitmap.
- encodeSameFamily: asks for image/png for a PNG, image/webp for a WebP, image/jpeg for JPEG and HEIC, at ENCODE_QUALITY 0.85; a WebP request that does not come back as WebP is encoded again as image/jpeg; a result whose type is not jpeg, png or webp gives null. defaultBrowserImageParts.encode paints a white ground only under image/jpeg, so a PNG keeps its transparency.
- planDownscale returns { width, height, scaled }. After this plan nothing reads `scaled` (prepareImage was its only reader; previewOf reads only width and height). MIME_OF_KIND is then read only for HEIC.
- images.test.ts helpers: RULES (maxBytes 10 MB, maxPixels 25 000 000, maxSide 12 000); JPEG_HEAD, PNG_HEAD, WEBP_HEAD, ftyp(major, ...compatible); fileOf(name, size = 1024, type = 'image/jpeg'); fakeParts({ head, width, height, decodeFails, encoded(type), encodeThrows, preview }) returns { parts, bitmap, close, encode }. The default encode gives a 500-byte Blob of the asked type; `encoded` overrides it.
- Callers (no edit needed, all send prepared.file): PhotoSlot.tsx (share picture and product line slots), GalleryPhotoModal.tsx, OrderPhotoPicker.tsx, OrderPhotosCard.tsx. Their component tests mock prepareImage, so they do not change.

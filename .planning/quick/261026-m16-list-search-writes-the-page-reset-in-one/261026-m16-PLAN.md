<objective>
Make a list search write its text and the page reset in ONE URL update, every time, by timing the 300 ms quiet-time wait inside the list hook instead of handing it to nuqs (owner ruling D-68, 2026-10-26). TDD: a deterministic failing test first, then the fix.

Purpose: nuqs 2.10.1 debounces each URL key on its own timer, so under CPU load `q` and the page reset can land as two URL updates (`?page=2&q=carmen` then `?q=carmen`). That failed main CI twice on useUsersListParams and, in the app, sends a short-lived extra request for page 2 of the new search on every createListParams list with a search (Users, Company Expenses, Deleted Expenses). It breaks the documented rule "a search resets the page in the same single URL update" (docs/web/url-state.md section 3).
Output: the fixed hook, new tests in createListParams.test.tsx, refreshed comments and docs, and quoted evidence (RED run, GREEN runs, 20 isolated runs, 3 full-suite runs, verify).

## Owner ruling

- **D-68 (owner, 2026-10-26, STATE.md):** fix the split in a small PR on branch `fix/list-search-single-update` (already checked out, from origin/main a8c408bf), not by re-running CI. Approved direction: the hook does the 300 ms quiet-time wait with a timer held in a ref; on expiry it writes `{ q, page: null }` in ONE nuqs update with `history: 'replace'` and no URL rate-limit option. `setSearch(text, { immediate: true })` cancels a waiting timer and writes at once. The timer is cleared on unmount. Other setters behave as today; reset cancels a waiting search.

## Root cause (confirmed by the planner in node_modules/nuqs/dist)

- `setSearch` today calls `setParams({ q, page: null }, { history: 'replace', limitUrlUpdates: debounce(300) })`.
- nuqs `useQueryStates` update (index.js about L569-610) pushes each key into `debounceController.push(...)` separately. `DebouncedPromiseQueue.push` (debounce-Ynq26WfO.js about L269-296) starts one `setTimeout(..., 300)` per key through `timeout()`, which calls the global `setTimeout` at call time. Each timer's flush pushes its key into the global ThrottledQueue and flushes it on a `setTimeout(0)`. Normally both 300 ms timers fire first and one URL update results; if the q flush runs before the page timer fires, two updates result.
- A write without the rate-limit option goes straight into the ThrottledQueue for all keys of the call and flushes once, so one `setParams` call with both keys is one URL update.

## Planner design choices (Claude's discretion; record them in the SUMMARY so the owner can see them)

1. **Keep "the hook shows the typed search at once".** Today nuqs applies `q` and the page reset to the hook's values immediately and only the URL waits. Readers that rely on that instant value: SearchBox (`value` prop, outside-change check), the search chips on UsersPage, ExpensesPage and DeletedExpensesPage (`values.q !== null`), useSettledListParams (debounces `values.q` 300 ms and holds the page reset with it), and ExpensesPage `isOutsideFilters` (reads `values.q` when an expense is saved). If the hook only changed `values` after its own 300 ms wait, useSettledListParams would wait another 300 ms (a search would take 600 ms) and the chips would lag. So the hook keeps the waiting view (`{ q, page: <page default> }`) in state and spreads it over the nuqs values until the write lands. The view equals what nuqs shows after the write, so the values, and the list query key, do not change at the write. With this, nothing that reads `values.q` changes behavior.
2. **A waiting search rides along with the next write.** If setFilter, setFilters, setPageSize, setPage or clampPage runs while a search waits, their own patch and history mode stay exactly as today, and the waiting search is written in the same single update (then the wait ends). Old nuqs behavior: a later write to the page key cancelled only the page part of the wait and `q` landed alone later. The end URL is the same for every setter; carrying it gets there in one update and never lets the URL disagree with what the screen shows. reset() and unmount drop the waiting search instead.

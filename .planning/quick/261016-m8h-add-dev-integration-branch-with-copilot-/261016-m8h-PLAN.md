Output: updated workflows, classifier, merge gate, merge script, a new `docs/operations/dev-ruleset.json`, Dependabot target, tests, and docs. Planner decisions (Claude's discretion, recorded so the orchestrator can confirm with the owner):
1. A pull request into `main` must have head `dev` from this repository (the release pull request). Anything else into `main` is refused. Consequence: any other open PR into main is retargeted to `dev` once `dev` exists (runbook step), and Dependabot version updates target `dev`. Bootstrap (owner, 2026-10-16): this change lands in its OWN branch cut from `main` AFTER Phase 3 PR #1 merges; Phase 3 is not retargeted. This one PR into main is merged from a `main` checkout so today's gate (which still allows any head into main) runs; the runbook says so.
2. The sync after a release goes through a short-lived `sync/<name>` branch cut from `dev` with `origin/main` merged into it, merged into `dev` with a merge commit. Reason: a pull request whose head is `main` itself can never be up to date with `dev` (a squash release never contains dev's own commits), so the locked strict "branch up to date" rule on `dev` (and the gate's own behind check) would block it forever, and GitHub's "Update branch" would have to write to `main`, which its ruleset forbids. The sync branch keeps every locked decision intact: main is merged into dev through a PR with a merge commit, and main becomes an ancestor of dev. The gate refuses a direct `main` into `dev` PR with a reason that points to this procedure.
</objective>

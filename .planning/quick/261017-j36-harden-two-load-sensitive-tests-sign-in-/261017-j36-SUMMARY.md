# Quick 261017-j36: Harden two load-sensitive tests Summary

The sign-in timing test now runs alone in its own non-parallel xunit collection with every branch warmed first, and the ESLint config test shares one ESLint instance with a 30 s budget. The 04-12 must-have (500 ms floor, 8 rounds, four branches, overall * 0.2) is unchanged.

## Cause analysis

`SignInHandler` waits until 500 ms after the branch's work, so a response takes max(work, floor). The floor hides branch differences only while every branch's work stays under 500 ms. The success branch does the most work (a second transaction in `StartChallengeAsync`: failed-count reset, challenge invalidation, code email render, three Data Protection `Protect` calls, challenge/outbox/audit inserts, commit). In a full `dotnet test --solution` run, the Server and Infrastructure integration assemblies and the architecture tests (publish and Release build) all hit the one LocalDB engine, so each database round trip queues and the branch with the most of them can pass the floor. The ESLint case paid the cold load of ESLint and its plugins inside the 5 s default and took 7.8 s in a full parallel run.

### Task 1 outcome: Case C (not reproduced, proceed)

The temporary probe (floor set to 1 ms, otherwise a copy of the timing test, never committed, deleted before the fix) measured each branch's own work. In the full run SignInTimingTests passed and the success work stayed under 400 ms, so the 2026-10-17 failure was not reproduced. The cause rests on the code analysis above plus the 2026-10-17 numbers (success median 863 ms vs overall 518 ms, max 3454 ms).

| Branch | Work median alone (ms) | Work median in full solution run (ms) |
|--------|------------------------|---------------------------------------|
| unknown | 65 | 176 |
| wrong | 96 | 202 |
| deactivated | 92 | 169 |

Every branch's work is roughly 2 to 3 times higher under load but still far under the 500 ms floor in this run. The 2026-10-17 failure therefore came from bursts: the probe full run's own timing line shows `max 2069 ms` for the timing test even though it passed, so a single stall of a second or more is enough. Probe rounds, alone: `113,69,71,104 | 64,133,105,130 | 63,135,64,129 | 65,104,113,68 | 64,69,92,69 | 65,89,91,91 | 63,118,125,74 | 68,68,93,117`. Full run: `215,226,189,198 | 187,263,169,161 | 158,150,158,183 | 191,217,177,185 | 183,266,191,299 | 169,156,146,201 | 148,188,169,191 | 163,183,138,162` (unknown, wrong, deactivated, success).

No 401 branch had a full-run work median of 400 ms or more, so there is no thin-margin owner observation from the medians. The worst single sample under load was 299 ms (success), and the pre-fix timing line shows a 2069 ms burst, so the floor's margin during a stall is the owner's call under D-39; the floor was not changed.

## Fix

- `SignInTimingTests` is in `[Collection(SignInTimingRunsAlone.Name)]`, defined with `DisableParallelization = true` in the same file, so it starts after every parallel collection in that assembly and nothing else in the assembly runs beside it.
- Each branch (unknown, wrong via a spare `warmWrong` account, deactivated, success) gets one unmeasured call before sampling.
- `sign-in-timing.txt` and the assertion message now list every round's four samples.
- `eslint-config.node.test.ts`: one module-scope `ESLint` instance, config resolution cached per file, `TOOL_LOAD = { timeout: 30_000 }` on both describe blocks. Names, the 25 `expect` calls and the 15 tests are unchanged.

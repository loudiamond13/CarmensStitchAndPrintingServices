## Audit log in WebKit: root cause (Task 1)

### Reproduction

Preflight before each run: all four ports free, no dev/test processes. Command: `npm --prefix web run e2e -- --grep @audit --project webkit --project iphone --workers 1 --trace on --reporter=line`. Result: **4 failed, 6 passed** (the prior note said three; I count four, two per project).

| Project | Test (audit-log.spec.ts) | Failing line | Assertion |
| ------- | ------------------------ | ------------ | --------- |
| webkit, iphone | line 160, "page and the filters of a link survive a trip to Users and Back..." | 173 | `getByRole('navigation', { name: 'Pagination' })` not found within 5s |
| webkit, iphone | line 243, "a Manager edits an expense amount and payer..." | 288 | `getByLabel('Done to')` expected enabled, received disabled (option "Loading staff...") |

The page snapshot at failure shows "Loading audit entries..." and both staff selects disabled. The other two @audit tests per project pass but sit close to the same 5s limit (see the timing below). Chromium with the same two tests and `--trace on`: 2 passed. Firefox and Pixel were not part of this repro command (the plan's Task 2 engine check applies only to Class A).

### Evidence, WebKit next to chromium (trace.zip expanded in the scratchpad)

- (a) Requests: **identical in both engines.** Each sends `GET /api/v1/audit-log?...` and `GET /api/v1/audit-log/people` once, right after the refresh, both **200**, complete, no cancel, no repeat. WebKit: audit-log 3,024 bytes, people **422,028 bytes**. Chromium: people 423,428 bytes.
- (b) Console, page errors, CSP: **none in either engine** apart from the two expected 401s on `/api/v1/auth/refresh` (the test declares them with `guard.expectStatus`). No CSP violation, no page error.
- (c) URL loop: **none.** One request each, no repeated navigation. The only repeats in the chromium trace are the intended ones after Users and Back.
- (d) The Users page before it loads fine in the same WebKit test (the tests reach and leave it). The shared session and client work.

So the data arrives and the page is simply late: the responses finish at about 0.5 s, and the Done by / Done to selects become enabled only seconds later.

### Hypotheses

1. **"The page is slow to render the staff list in WebKit because the people list is huge, and the shared `CSPS_E2E` database has grown to 4,603 people (every e2e test creates staff and nothing removes them). The default 5s expect timeout is hit." Confirmed.** Tests of it (temporary probes in `web/e2e`, route-truncating the people response to N people, one WebKit and one chromium run each, probes deleted):

| People shown | chromium: Done to enabled | webkit: Done to enabled |
| ------------ | ------------------------- | ----------------------- |
| 50 | 468 ms | 684 ms |
| 500 | 351 ms | 972 ms |
| 2000 | 417 ms | 1965 ms |
| 4600 (all) | 582 ms | **7354 ms** |

   A direct measurement of the full page (no truncation): chromium 650 ms, webkit 7191 ms to enable. Cost grows faster than linearly in WebKit and stays flat in chromium. The same two selects hold 9,300 options in total.

2. **Narrowing: "WebKit is slow when options are added one at a time to a select that is already on the page" (what React does when the list arrives after the first render). Confirmed** with a plain DOM probe that uses no app code:

| Options | chromium live / detached | webkit live / detached |
| ------- | ------------------------ | ---------------------- |
| 1000 | 21 ms / 20 ms | 182 ms / 17 ms |
| 2000 | 35 ms / 34 ms | 665 ms / 40 ms |
| 4000 | 70 ms / 78 ms | **2269 ms / 58 ms** |

   ("live" = appended into a select already in the document; "detached" = same options built first, then attached.) A plain build of 2 x 4,600 options in one go costs WebKit only 454 ms, so the app is not doing anything odd: this is quadratic behavior in the Playwright (Windows) WebKit build when options are inserted into an attached select. The same two selects take the whole main thread, which is why the entries table also shows "Loading audit entries..." until they finish.

No hypothesis was refuted. Two were needed to explain it.

### Cause and class

- Cause: `AuditLogPage.tsx` renders the Done by and Done to selects from `useAuditPeopleQuery()` (lines 152 and 184 to 190). With 4,603 people, WebKit takes about 7 s to insert about 9,300 options into live selects, longer than the spec's 5 s `toBeEnabled` and `Pagination` waits. Chromium takes 0.6 s.
- **Class B (harness data volume plus WebKit engine behavior), classed with moderate confidence.** Reasons: (1) The trigger is the e2e database holding 4,603 people, which real production data does not (a few dozen staff plus former staff). With up to 2,000 people the page is fast enough in WebKit. (2) Real Safari shares WebKit's engine code, so very large lists could be slow there too, but I could not verify that on real Safari from this machine, and I have no evidence a real Manager ever sees more than dozens of names. Per the plan, a cause that cannot be classed with confidence is treated as Class B and the owner decides.
- The audit-log code, the URL rules and the CSP are not at fault. No hypothesis pointed at them.

## Options that were offered (resolved by D-77)

**WebKit audit-log failures (4 tests: webkit and iphone, lines 160 and 243 of `web/e2e/audit-log.spec.ts`).** Cause: the shared `CSPS_E2E` database now holds 4,603 people, and Playwright's Windows WebKit takes about 7 s to insert the 9,300 select options (chromium 0.6 s), over the spec's 5 s wait. The app and the audit URL rules are fine. Nothing was changed. Options, recommendation first:

1. **Recommended: reset `CSPS_E2E` at the start of each e2e run (a harness change you approve).** Reason: it fixes the cause (data that only grows), keeps every spec as written, and makes every engine faster and more repeatable. It touches only `CSPS_E2E`, so no `BetsLLC_*` database is involved.
2. **Give the audit-log waits a longer timeout in `audit-log.spec.ts`.** Reason: smallest change, but it hides the growth and the next thousand test users will push it over again.
3. **Make the app build the staff options in one step (a small `key` change so React attaches the select with its options already inside), or cap and search a very long list.** Reason: it would also help any real Safari user with a huge list, but real data has a few dozen people, it needs a decision on look and behavior for the cap/search variant, and the one-step variant is only an unmeasured guess until tried. Not done without your word.

I did not verify on real Safari. If you want that confirmed, the Class A question is whether a real Safari slows down the same way with thousands of options.
